# Claude Code と Codex の分担

状態: 草案(2026-11-01)

Claude Code が作業を決めて指示書を書き、Codex が実装し、実装のあとに Claude Code がレビューしてコミットする。[agents/README.md](README.md) の「移植を進める」の手順と、[台帳](../docs/bug-ledger.md)の B の修正を、担当で分けたもの。

## 1. 対象と根拠

| 作業 | 指示書の根拠 | 依頼してよい条件 |
| --- | --- | --- |
| Rust への移植(C) | プランの手順6の1項目 | プランが承認済み |
| B のバグ修正(C++) | 台帳の1行 | 台帳の決定が「B で直す」(人の判断)。1件を1回の依頼にする |

どちらにも当たらない作業(決定のない台帳の行、プランのない移植)は依頼しない。

## 2. 担当

| 段階 | 担当 | 内容 |
| --- | --- | --- |
| 作業を決める | Claude Code、承認は人 | 移植はプランを[ひな形](plans/template.md)から作り、文脈を持たない subagent のレビューを経て人が承認する。B の修正は台帳の決定を待つ |
| 実装 | Codex | 指示書を受けて1回起動する。テストを先に書き、Red を確かめてから実装する |
| レビュー | Claude Code(R3 は文脈を持たない subagent) | 4節。通るまで次の指示書を出さない |
| コミットと記録 | Claude Code、承認は人 | 移植はチェックボックスに根拠のコミットを書き、実施記録をプランに書く。B の修正は修正を1コミットにし、開発用の2本の比較と台帳の記録を別のコミットにする(`86911cb` と `96c2ca8` の形)。状態が変わるなら docs/README.md も同じコミットで直す |

Codex はコミットしない。Claude Code はレビューの段階で実装を直さない。直すべき点は差し戻す。

## 3. 実装の依頼

1. [指示書のひな形](handoff/brief-template.md)を、Claude Code のスクラッチパッドに写して埋める
2. 作業ツリーがきれいなこと(`git status --short` が空)を確かめ、HEAD のコミットを控える
3. Claude Code が Bash で、バックグラウンドで実行する

```bash
agents/handoff/run_codex.sh new <指示書> <スクラッチパッド>/<名前>
```

出力は `<名前>.report.json`(Codex の報告。形式は [report.schema.json](handoff/report.schema.json))、`<名前>.events.jsonl`(Codex が実際に走らせたコマンドと終了コード)、`<名前>.session`(セッション ID)。差し戻しは同じセッションを再開する。

```bash
agents/handoff/run_codex.sh resume "$(cat <前の名前>.session)" <修正の指示書> <スクラッチパッド>/<新しい名前>
```

### Docker を使えるようにする設定

`run_codex.sh` は Codex を `workspace-write` のサンドボックスで起動し、`sandbox_workspace_write.network_access=true` を付ける。これがないと、Docker のクライアントが `/var/run/docker.sock` に接続できない(`permission denied`)。2026-11-01 に、`docker version`(29.9.2)と `rust/run.sh fmt --all -- --check` が新規と再開の両方で終了0になることを確かめた。

この設定で Codex に渡る権限:

- ネットワークに出られる
- Docker のデーモンを通じて、ホストのどこでも読み書きできるコンテナを起動できる。サンドボックスの書き込みの制限(作業ディレクトリと `/tmp` だけ)は、Docker 経由では効かない

したがって、リポジトリの外を変えないことは、指示書の禁止事項と R1 の確認で守る。R1 が見るのはリポジトリの中だけで、リポジトリの外への書き込みは検出できない。

モデルは `~/.codex/config.toml` の既定に従う(`CODEX_MODEL` で替えられる)。古い CLI は新しいモデルを拒む: 0.157.1 では `gpt-6.1-sol` が 400 `model_not_found` になり、0.166.0 では通った(2026-11-01)。拒まれたら、まず `codex update` を試す。

## 4. レビュー

Codex の報告を受けたら、R1〜R4 を順に行う。結果は移植ならプランの実施記録に、B の修正なら記録のコミットの本文に書く(指摘、対応、判定)。

| 段階 | 確かめること | 落とす条件 |
| --- | --- | --- |
| R1 範囲 | `git diff --stat` と `git status --short` が、指示書の「変更してよいファイル」に収まる。HEAD が控えたものから動いていない | 一覧の外の変更。禁止事項(指示書の5節)への変更。コミットされている |
| R2 報告の照合 | 報告の `commands` を、events の JSONL の `command_execution` と突き合わせる。そのうえで Claude Code が検証のコマンドを自分で走らせ、終了コードと結果を比べる。Red は、実装のファイルだけを `git stash push -- <実装のファイル>` で退避し、テストが報告どおりに落ちることを確かめてから `git stash pop` で戻す | events にないコマンドが報告にある。結果が報告と違う。Red が再現しない |
| R3 独立レビュー | 文脈を持たない subagent に、差分と判定の基準(移植はプランと関係するルール、B の修正は台帳の行と関係するルール)だけを渡す。指示書・Codex の報告・ここまでの経緯は渡さない | 正しさの指摘(演算順・分岐・境界・unsafe など)が残る |
| R4 判定 | R1〜R3 の指摘を、Claude Code が根拠(プランの詳細設計、台帳の決定)と照らして「直す/直さない(理由)」に分ける | — |

B の修正では、R4 の通過のあと、修正をコミットしてから、開発用の2本を `eval/run_offline.sh` で走らせて修正前の B と比べ、台帳に記録する(Claude Code)。

判定:

- **通過**: 差分・検証の結果・未検証の範囲を人に示し、承認を得てコミットする
- **差し戻し**: 指摘ごとにファイル・行・期待する状態を書いた修正の指示書を、3節の再開で渡す。差し戻しは2回まで。3回目が要るときは人に判断を仰ぐ(プランか台帳の決定の不備の可能性がある)
- **止める**: Codex が止まる条件(指示書の6節)で止まった、または指摘が許容誤差・ゴールデン出力・バグの扱いの判断に関わる。人に判断を仰ぐ

Codex の報告の `ledger_candidates` は、台帳への起票候補として人に示す。Claude Code が台帳に書くのは、人が起票を決めてから。
