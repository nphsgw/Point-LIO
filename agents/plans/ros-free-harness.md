## 1. 概要

評価 bag 2本から点群と IMU を時刻順にファイルへ書き出し、C++ と将来の Rust の双方に同じ入力を渡せる実行経路を作る。C++ 側は `ros::init`・購読・`spin`・発行を使わずに、ファイルを読んで最後まで走り、軌跡(と地図)をファイルに出す。

完了条件は2つ。

1. ファイル駆動の実行が、改造前の ROS 実行と、事前登録の規則で決めた幅の中で一致する。
2. 改造後の ROS 経路(`pointlio_mapping`)が、改造前と同じ結果幅に収まる。

これは計画書フェーズ0の項目2であり、フェーズ0の項目4(A の10回実行)の前提になる。

## 2. 背景

- 事前登録は、性能の数値をハーネスができるまで登録対象にしないと決めている。実時間の `rosbag play` は再生速度の影響を受ける。
- 以前、同じ bag の avia で終点と始点の距離が 0.04 m と 0.071 m に変わったことがある。rviz 付きの `mapping_<sensor>.launch` での観測で、`eval/run_cpp.sh` とは条件が違う(原因は未確認)。
- 手順0(2026-10-25、HEAD `29f045e`、`eval/run_cpp.sh`、Docker、実時間の `rosbag play`、16 コア機)では、各 bag の10回の `traj.tum` が SHA256 で一致した(姿勢数 avia 487、ouster 1985。`loop back` は全 run で 0 件)。この条件では、少なくとも10回に限って ROS 経路は決定的だった。10回で一致しても、1回あたり揺れる確率が約 26% 未満(95%)と言えるだけで、まれな競合は排除できない。
- 手順0b(2026-10-25、HEAD `a64d93c`。C++ のソースは `29f045e` と同じ)では、各 bag で再生速度 0.5 倍・2 倍(`PLAY_RATE`)と、全コアに busy loop を16本走らせた条件を各3回、計18回実行し、すべて手順0の `traj.tum` と SHA256 で一致した(`loop back` は全 run で 0 件)。負荷条件の実際の CPU 使用率は測っていない。rviz 付きの条件は未実施で、上の 0.04/0.071 m の揺れは再現していない。
- 決定的に見える理由の仮説(未検証。2 倍速と負荷でも揺れなかったため、これだけでは説明しきれない): 実時間再生では1フレームの処理が次のフレームの到着前に終わり、`sync_packages` の時点のキューの状態が毎回同じになる。rviz などの負荷でメインループが遅れると、IMU の溜まり方が変わって揺れる、という説明と上の観測は矛盾しない。
- コードを読んで確認した、非決定性の候補:
  - `main()` は `AsyncSpinner(0)` を起動し、同じループで `ros::spinOnce()` も呼ぶ。購読コールバック(`lidar_buffer`、`time_buffer`、`imu_deque` に書く)と、メインループ(同じキューを読んで `pop_front` する)が別スレッドで動く。
  - 排他制御はない。`mtx_buffer` の lock は [li_initialization.cpp](../../src/li_initialization.cpp) のコールバックでコメントアウトされている。データ競合の疑いであり、バグ台帳の起票候補。ここでは直さない。手順0の条件では結果に表れなかったが、疑いは消えていない。
  - スレッド数: CMake がビルド時に `nproc` から `MP_EN`・`MP_PROC_NUM` を定義する(16 コアの本機では 4)。ただし `src/`・`include/` のどこにもこれらの参照、`#pragma omp`、`omp_set_num_threads` はなく、使われている OpenMP 関数は `omp_get_wtime` だけである(確認済み)。したがって、OpenMP によるコード内の並列化は非決定性の原因ではない。Eigen や PCL が `-fopenmp` のもとで内部的に OpenMP を使うかは未確認。手順0で `OMP_NUM_THREADS=1` と既定値の差を実測して報告する。事前登録の「`MP_PROC_NUM` を固定」の扱いは、この結果とともに人に報告して決める(§9)。

## 3. 詳細設計

### 3.1 構成(決定: ノード機構のみ除去)

ROS 型は残し、ノード機構だけを外す。

| 層 | 内容 |
| --- | --- |
| 抽出器 | bag → 入力ファイル。Python。ROS 環境(Docker)内で実行 |
| 入力ファイル | 1つの順序付きバイナリ。形式は §3.2 |
| 共有ライブラリ | 既存の前処理・IMU 処理・推定・iVox。購読・発行から切り離す |
| `pointlio_mapping`(既存) | ROS ノード。挙動を変えない |
| `pointlio_offline`(新規) | 入力ファイルと設定 YAML を読み、軌跡を書く |

`pointlio_offline` は `sensor_msgs`・`livox_ros_driver` のメッセージ型と `ros::Time` にはリンクするが、roscore もノードも使わない。メッセージ型の完全除去は今回の範囲に入れない。理由は、前処理(`pcl::fromROSMsg`、`PointCloud2` のフィールド走査)を作り直すことになり、等価性の検証範囲が大きく広がるため。Rust 版は入力ファイルから直接読むので、C++ 側の型は Rust の入力の妨げにならない。

### 3.2 入力ファイル形式(決定: 案 A の独自バイナリ)

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. 独自の単純バイナリ(採用) | C++・Rust とも依存なしで読める。仕様が小さい | 仕様書と読み書きの実装を自前で持つ |
| B. MCAP | 既存規格、ツールあり | 依存が増える。ROS1 メッセージの解釈が結局要る |
| C. テキスト(CSV 等) | 目で確認しやすい | 点群が巨大(Ouster 1991 フレーム)。浮動小数の往復で値が変わる恐れ |

案 A の内容(メッセージを時刻順に並べた列。各レコードは種別・ヘッダ時刻(sec, nsec)・ペイロード長・ペイロード):

- IMU: 角速度、線加速度、ヘッダ時刻。`orientation` と共分散はコードが読まない(確認済み: [IMU_Processing.cpp](../../src/IMU_Processing.cpp) は `linear_acceleration`・`angular_velocity`・`header.stamp` だけを使う)。ただし保存は全フィールドとし、T2 は全フィールド一致で照合する。
- `PointCloud2`: `height`、`width`、`point_step`、`row_step`、`is_bigendian`、`fields`(名前、offset、型、count)、生の `data`。型ごとの前処理を Rust 側も移せるよう、前処理前の生データを保存する。
- Livox `CustomMsg`: `timebase`、`point_num`、`lidar_id`、各点の `offset_time`、`x`、`y`、`z`、`reflectivity`、`tag`、`line`。前処理が使うのは `offset_time`・`x`・`y`・`z`・`reflectivity`・`tag`・`line` とヘッダ時刻。`timebase`・`point_num`・`lidar_id` の使用は未確認だが、保存はする。
- 並び順の基準は bag の記録時刻(ヘッダ時刻ではない)。種別をまたいだ順序も保存する。ヘッダ時刻は検証対象なので書き換えない。
- 時刻の逆転したメッセージは、入力ファイルから除かずそのまま残す。ROS 経路と同じく、受信処理側で捨てる(§3.4)。

### 3.3 設定

ROS の設定は launch のインライン `<param>` と YAML に分かれる。同じ値を保証するため、ROS 実行中に `rosparam dump /laserMapping` で得たものを、センサごとの正準設定として `eval/config/` に置く。`pointlio_offline` はこれを読む。`readParameters(ros::NodeHandle&)` の `nh.param` 呼び出しを、読み込み元を差し替えられる形にする。YAML の読み込みには yaml-cpp を使う(イメージに libyaml-cpp-dev 0.6.2 が入っていることを確認済み)。

### 3.4 送り込みの方針と、ROS 経路から引き継ぐ挙動(要確認)

ROS 実行では、コールバックとメインループが並行し、メインループは 500 Hz でポーリングする。ファイル駆動では、レコードを1件ずつ決まった順序で積み、積むたびにメインループの本体を1回回す。この方式は ROS 実行の「再生が十分遅く、ループが追いつく」状態に近いが、同一とは限らない。IMU の先読みに依存する分岐(`imu_deque` が空かどうか、`laserMapping.cpp` 739 行付近など)で差が出うる。差の大きさを §5 の試験で測り、事前登録の規則で受け入れ可否を決める。

ROS 経路から変えずに引き継ぐ挙動(確認済み。いずれもコードを読んだ範囲):

- `imu_cbk` は IMU 時刻から `timediff_imu_wrt_lidar` と `time_lag_IMU_wtr_lidar` を引く(今回の設定では 0.0)。この処理は受信処理側に残し、ファイルの時刻は生のまま保つ。
- 時刻が逆転した LiDAR・IMU メッセージは、コールバックが黙って捨てる(LiDAR は `scan_count` を先に増やす)。この判定と `scan_count` の増え方をそのまま保つ。ファイル駆動で捨てた件数を ROS 経路と比べる(T12)。
- `cut_frame_init`・`con_frame` は両 config で無効なので、今回の bag では通らない。分岐は壊さずに残すが、検証はしない(未検証の範囲に記録)。
- `flg_reset` は `true` を代入する箇所がなく、リセット経路は到達しない(死んだコード)。挙動を変えずに残す。
- 終端: 最後の LiDAR フレームは、`last_timestamp_imu >= lidar_end_time` になるまで `sync_packages` が `false` を返し続ける。入力が尽きた時点で処理されていないフレームは、ROS 経路と同じく処理しない。件数は T10 で ROS 経路と比べる。

### 3.5 出力

- 軌跡: ROS 版が `/aft_mapped_to_init` に出す姿勢と同じ時刻・値を、TUM 形式で書く。`publish_odometry` は3箇所(`laserMapping.cpp` 714、907、1007 行)から呼ばれ、`static tf::TransformBroadcaster` による `tf` 送信も含む。書き出し先に差し替える対象は、`tf` 送信も含めて切り離す。
- 地図: 事前登録の Chamfer 距離のため、「最終地図」を次のとおり定義する(決定。§9)。事前登録の文言は改訂済み(`b626613`)。
  - 内容(累積は `scan_pub_en`・`pcd_save_en` と独立に常に行う。ROS 側の呼び出し条件 `scan_pub_en || pcd_save_en` を引き継がない): `publish_frame_world` が呼ばれる各フレームの `feats_down_world`(ダウンサンプル済みのワールド点)を全フレーム累積し、最後に1回だけ書く。iVox の内容は使わない。
  - 初期地図の構築中のフレームは `continue` で `publish_frame_world` に届かないため、含まれない(挙動をそのまま引き継ぐ。ROS 経路の `pcd_save` と同じ範囲)。
  - 既存の `pcd_save` の挙動(判明していること、確認済み):
    - 書き出しは `publish_frame_world` の中にあり、ROS の発行処理と同じ関数にある。ハーネスは書き出しを切り離し、累積だけを `pointlio_offline` 側に置く。
    - `pcd_save_interval = -1` では `scan_wait_num >= -1` が毎回真になり、毎フレーム `ROOT_DIR/PCD/scans_N.pcd` を書いて消す。`config` のコメント(-1 は1ファイル)と異なる。実行では未確認。ハーネスはこの挙動を流用しない。
    - 終了時の `scans.pcd` は、積んだ点が残っている場合しか書かれない(上の挙動では通常は書かれない)。
  - 未確認: `publish_frame_world` を呼ぶ時点の `feats_down_world` が、更新後の姿勢で変換された点か。T14 の前に確認する。
  - 性質: 点は推定姿勢で変換しただけなので、Chamfer は軌跡の差にほぼ従属する(ATE/RPE と情報が重なる)。
- 書き込み先は引数で指定する。`open_file()` が `ROOT_DIR/Log/` に書く(読み取り専用マウントでは黙って失敗する)ため、デバッグ出力の出力先も切り離す。`Log/pos_log.txt`(`fopen` の戻り値を検査していない。`runtime_pos_log` が真だと NULL で落ちうる)も同様に扱い、`pointlio_offline` では `runtime_pos_log` を偽に固定する。

## 5. 新規テストケース

許容誤差は結果を見る前に決める。下の幅は、事前登録の「基準幅 τ」の規則(10回実行どうしの全組の最大値)を、改造前 ROS 実行に適用して得る。数値はここでは置かない。

手順0の実行結果を見る前に、次を固定する(このプランの時点で決めた)。

- 中央値実行: 10回のうち、他の9回との ATE の中央値が最小の1回(事前登録と同じ規則)。
- 指標: ATE(SE(3) 整列、スケールなし)、RPE 並進・回転の区間 10 m と 10 フレーム(evo に秒単位がないための代用。事前登録の「1 s」と異なる点は報告に明記する)。基準幅は指標ごとに、組ごとの値の最大値。
- 命名: この幅は `tau_harness`(ハーネス検証用)と呼び、事前登録の τ と区別する。`tau_harness` の値は、事前登録の τ の代わりに使わない。
- `tau_harness` が、評価精度に比べて大きく、検出力が乏しい場合(目安は ouster の ATE と同程度以上)は、合否の意味を限定して報告する。何を「大きい」とするかは、手順0の結果を見る前に決められないため、そのときに人に確認する。

手順0の結果と、それを受けた扱い(2026-10-25、人の判断。§9 の決定6):

- 各 bag の10回の `traj.tum` はビット一致した(§2)。全組の ATE は avia 約 1e-16 m、ouster 約 7e-15 m、RPE は 0〜1e-15 台。入力が同一なので、これは実行間の差ではなく evo の整列計算の丸めである。
- 事前登録の規則5(τ が0に近くても下限を設けず、そのまま使う。ビット一致までは求めない)をそのまま適用する。`tau_harness` は上の実測値(指標ごと、bag ごとの全組の最大値)とする。結果を見た後に下限を置くこと、負荷をかけた条件の揺れで幅を広げることはしない。
- T7・T8・T14 は、`tau_harness` を超えたら不合格とする。不合格の場合は、最初に食い違う姿勢を特定して、原因(送り込み順序の差(§3.4)か、改造・移植の誤りか)を報告する。
- 中央値実行は、全10回が同一のため、どれを選んでも同じ(run01 を使う)。
