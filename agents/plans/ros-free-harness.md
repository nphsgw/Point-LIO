# プラン: ROS 非依存の実行ハーネス

状態: レビュー待ち(人の判断は反映済み。実装前に別セッションでレビューする)
元資料: [計画書 フェーズ0 項目2](../../docs/rust-reimplementation-verification-plan.md)、[指標と許容誤差の事前登録](../../docs/metrics-preregistration.md)、[評価データ](../../docs/evaluation-data.md)

「確認済み」はコードを読んだ範囲、「要確認」は未決定または未検証を指す。

## 1. 概要

評価 bag 2本から点群と IMU を時刻順にファイルへ書き出し、C++ と将来の Rust の双方に同じ入力を渡せる実行経路を作る。C++ 側は `ros::init`・購読・`spin`・発行を使わずに、ファイルを読んで最後まで走り、軌跡(と地図)をファイルに出す。

完了条件は2つ。

1. ファイル駆動の実行が、改造前の ROS 実行と、事前登録の規則で決めた幅の中で一致する。
2. 改造後の ROS 経路(`pointlio_mapping`)が、改造前と同じ結果幅に収まる。

これは計画書フェーズ0の項目2であり、フェーズ0の項目4(A の10回実行)の前提になる。

## 2. 背景

- 事前登録は、性能の数値をハーネスができるまで登録対象にしないと決めている。実時間の `rosbag play` は再生速度の影響を受ける。
- 現状の ROS 実行は非決定的に見える。同じ bag の avia で終点と始点の距離が 0.04 m と 0.071 m に変わった(原因は未確認)。
- コードを読んで確認した、非決定性の候補:
  - `main()` は `AsyncSpinner(0)` を起動し、同じループで `ros::spinOnce()` も呼ぶ。購読コールバック(`lidar_buffer`、`time_buffer`、`imu_deque` に書く)と、メインループ(同じキューを読んで `pop_front` する)が別スレッドで動く。
  - 排他制御はない。`mtx_buffer` の lock は [li_initialization.cpp](../../src/li_initialization.cpp) のコールバックでコメントアウトされている。データ競合の疑いであり、バグ台帳の起票候補。ここでは直さない。
  - スレッド数は CMake がビルド時に `nproc` から決める(16 コアの本機では `MP_PROC_NUM=4` の OpenMP)。実行時には変えられず、事前登録の「A は既定値と1スレッドの両方を測る」には CMake 側の手当てが要る(§8)。

## 3. 詳細設計

### 3.1 構成(決定: ノード機構のみ除去)

ROS 型は残し、ノード機構だけを外す。

| 層 | 内容 |
| --- | --- |
| 抽出器 | bag → 入力ファイル。Python。ROS 環境(Docker)内で実行 |
| 入力ファイル | 1つの順序付きバイナリ。形式は §3.2 |
| 共有ライブラリ | 既存の前処理・IMU 処理・推定・iVox。購読・発行から切り離す |
| `pointlio_mapping`(既存) | ROS ノード。挙動を変えない |
| `pointlio_offline`(新規) | 入力ファイルと設定 YAML を読み、軌跡を書く |

`pointlio_offline` は `sensor_msgs`・`livox_ros_driver` のメッセージ型と `ros::Time` にはリンクするが、roscore もノードも使わない。メッセージ型の完全除去は今回の範囲に入れない。理由は、前処理(`pcl::fromROSMsg`、`PointCloud2` のフィールド走査)を作り直すことになり、等価性の検証範囲が大きく広がるため。Rust 版は入力ファイルから直接読むので、C++ 側の型は Rust の入力の妨げにならない。

### 3.2 入力ファイル形式(決定: 案 A の独自バイナリ)

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. 独自の単純バイナリ(採用) | C++・Rust とも依存なしで読める。仕様が小さい | 仕様書と読み書きの実装を自前で持つ |
| B. MCAP | 既存規格、ツールあり | 依存が増える。ROS1 メッセージの解釈が結局要る |
| C. テキスト(CSV 等) | 目で確認しやすい | 点群が巨大(Ouster 1991 フレーム)。浮動小数の往復で値が変わる恐れ |

案 A の内容(メッセージを時刻順に並べた列。各レコードは種別・ヘッダ時刻(sec, nsec)・ペイロード長・ペイロード):

- IMU: 角速度、線加速度。`orientation` と共分散をコードが読むか未確認(要確認。使うなら保存する)。
- `PointCloud2`: `height`、`width`、`point_step`、`row_step`、`is_bigendian`、`fields`(名前、offset、型、count)、生の `data`。型ごとの前処理を Rust 側も移せるよう、前処理前の生データを保存する。
- Livox `CustomMsg`: `timebase`、`point_num`、`lidar_id`、各点の `offset_time`、`x`、`y`、`z`、`reflectivity`、`tag`、`line`。
- 並び順の基準は bag の記録時刻。タイムスタンプ(ヘッダ時刻)は検証対象なので書き換えない。

### 3.3 設定

ROS の設定は launch のインライン `<param>` と YAML に分かれる。同じ値を保証するため、ROS 実行中に `rosparam dump /laserMapping` で得たものを、センサごとの正準設定として `eval/config/` に置く。`pointlio_offline` はこれを読む。`readParameters(ros::NodeHandle&)` の `nh.param` 呼び出しを、読み込み元を差し替えられる形にする。YAML の読み込みには yaml-cpp を使う(イメージに libyaml-cpp-dev 0.6.2 が入っていることを確認済み)。

### 3.4 送り込みの方針(要確認)

ROS 実行では、コールバックとメインループが並行し、メインループは 500 Hz でポーリングする。ファイル駆動では、レコードを1件ずつ決まった順序で積み、積むたびにメインループの本体を1回回す。この方式は ROS 実行の「再生が十分遅く、ループが追いつく」状態に近いが、同一とは限らない。IMU の先読みに依存する分岐(`imu_deque` が空かどうか、`laserMapping.cpp` 739 行付近など)で差が出うる。差の大きさを §5 の試験で測り、事前登録の規則で受け入れ可否を決める。

### 3.5 出力

- 軌跡: ROS 版が `/aft_mapped_to_init` に出す姿勢と同じ時刻・値を、TUM 形式で書く(`publish_odometry` の出力を書き出し先に差し替える)。
- 地図: Chamfer 距離に必要。既存の `pcd_save` 経路が ROS 非依存かは未確認(要確認)。
- 書き込み先は引数で指定する。`open_file()` が `ROOT_DIR/Log/` に書く(読み取り専用マウントでは黙って失敗する)ため、デバッグ出力の出力先も切り離す。

### 3.6 差異・注意

| C++ の対象 | 変更 | 注意 |
| --- | --- | --- |
| `src/laserMapping.cpp`(`main`、`publish_*`) | ループ本体を関数にくくり出し、発行先を差し替え可能にする | 700 行のループが発行・状態と絡む。行の並べ替えをしない |
| `src/li_initialization.cpp`(コールバック) | 受信処理を、型を受けて積む関数に分ける | 時刻の逆転判定、`lidar_type` 分岐を保つ |
| `src/parameters.cpp` | 読み込み元を差し替え可能に | 既定値を変えない |
| `CMakeLists.txt` | `pointlio_offline` を追加 | 既存ターゲットのフラグを変えない |

## 4. テスト影響範囲

- 維持する挙動: `pointlio_mapping` の入出力、トピック名、パラメータ名と既定値。
- 既存のテスト・ゴールデン出力は未整備なので、影響を受けるものはない。
- 改造前の ROS 実行を、基準として先に保存する(§6 の手順0)。改造後の ROS 経路の判定は、この保存結果との比較で行う。

| 要件 | 前提・入力 | 操作 | 期待結果 | 出典 | 種別 |
| --- | --- | --- | --- | --- | --- |
| T1 抽出の件数 | 2 bag(SHA256 一致) | 抽出し、種別ごとに数える | avia: IMU 9953、LiDAR 491。ouster: IMU 19902、LiDAR 1991 | `rosbag info`(確認済み) | 結合 |
| T2 抽出の完全性 | 同上 | 先頭・末尾・等間隔の各 N 件を、bag の値と全フィールド比較 | 全フィールドがビット一致 | bag 自体 | 結合 |
| T3 抽出の決定性 | 同上 | 2回抽出 | ファイルの SHA256 が一致 | — | 結合 |
| T4 時刻の単調性 | 入力ファイル | 種別ごとのヘッダ時刻を検査 | 単調非減少 | 性質 | 性質 |

| T6 前処理の同値 | 同じメッセージ | ROS メッセージ経由と、ファイル経由で `Preprocess::process` を実行 | 全フレームの出力点群(座標・`curvature`)がビット一致 | 改造前の C++ | 結合 |

- T2・T5: リーダの1フィールドを壊した版で落ちること。
- T6: 前処理の入力から時刻フィールドを落とした版で落ちること。

ループ内の照合は、件数も検査する(空の入力で通らないように)。

## 6. 実装順

0. **基準の保存**: 現 HEAD で `eval/run_cpp.sh` を各 bag に10回実行し、結果(TUM、`meta.txt`、`build.log`)を保存する。τ_ROS をここで確定する。これは A のベースライン(フェーズ0項目4)の予行を兼ねるが、事前登録の τ そのものではない(§9)。
1. **正準設定**: `rosparam dump` を取り、`eval/config/` に置く。
2. **抽出器と形式の仕様書**: T1〜T4 を先に書き、Red を確認してから実装する。
3. **C++ リーダ**: T5。
4. **発行・購読の切り離し**: まず発行側(`publish_*` を出力先の差し替えに)、次に購読側。1段ごとに ROS 経路で T8 相当の簡易確認(軌跡の姿勢数と最終位置)を行う。
5. **`pointlio_offline`**: T6、T7、T10、T9。
6. **レビュー**: プランを別セッションでレビュー(実装前)。差分を別セッションでレビュー(実装後)。

並列作業は想定しない。`laserMapping.cpp` と `li_initialization.cpp` を同時に触る作業は直列にする。

## 8. スコープ外

- Rust 側の入力リーダ(フェーズ3で書く。形式の仕様書は今回渡す)。
- 見つかったデータ競合(§2)の修正。バグ台帳への起票候補として報告する。
- スレッド数を実行時またはビルド時の指定にする CMake の変更。事前登録の「A は既定値と1スレッド」を実現するために必要だが、ビルド構成の変更として別に扱う。
- 性能計測(フレーム単位の時間、メモリ)。出力の差し替え点は計測を足せる形にするが、計測自体は入れない。
- メッセージ型の除去、ROS ノードの構造改善、最適化。
- 事前登録の改訂(RPE 1 s を evo で出せない件)。人の承認が要る。

## 9. 決定事項と要確認

決定(2026-10-24、人の判断):

1. 入力ファイルの形式は独自バイナリ(案 A)。
2. ROS 型を残す範囲は、ノード機構のみ除去。
3. T7・T8 の許容幅に、改造前 ROS 10回の幅(τ_ROS)を、ハーネス検証用の別枠として使う。事前登録の τ(A の10回実行から導く)とは別物として扱い、混ぜない。ハーネス完成後の A の経路をファイル駆動にするかは、τ を導く時点で改めて決める。
4. 設定の読み込みに yaml-cpp を使う。

要確認:

- 送り込みの方針(§3.4)。T7 が τ_ROS を超えた場合の対処(方針の見直しか、差の原因調査か)は、そのとき報告して決める。
- IMU の `orientation`・共分散をコードが読むか(§3.2)。
- 既存の `pcd_save` 経路が ROS 非依存か(§3.5)。
