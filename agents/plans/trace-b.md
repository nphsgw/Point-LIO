## 1. 概要

B(C++)の `pointlio_offline` に、仕様のトレース(`trace.bin`。完全と発散の検査の2種類)を書く処理を入れる。あわせて、形式の検証器、B の段階の再実行の道具、照合器(J1・J2 と、J3・J4 の差の有無)を作り、仕様 §8 の完了条件1〜3を両 bag で確かめる。計画書のフェーズ0の「§5 のトレースの完了条件3つ」に当たる。

終わると、次のことができる。

- B の各段階の入口と出口を記録から読み、前処理から後の範囲の L2(J1〜J4)の基準にする
- C の範囲のプランで、C の書き手を同じ形式で作り、同じ検証器と照合器で B と比べる

### 3.2 記録を有効にする仕組みと終了コード

- 書き手は、実行時の引数で作る1つの大域のオブジェクト(`g_trace`。無効なら null)にする。記録の呼び出しはどれも `if (g_trace) …` の形にし、無効のときは値を読まない。
- 有効と無効は同じバイナリで切り替える(仕様 §1)。分岐を足すので機械語は変わる。変わっても出力が変わらないことは完了条件1で確かめる。
- 終了コード。トレースの停止は専用の例外の型で伝え、`main` の既存の `catch`(1 を返す)より前で受ける。

| 終了コード | 意味 | 終わりのレコード |
| --- | --- | --- |
| 0 | 正常 | 理由 0 |
| 1 | 既存の例外(設定の誤りなど) | なし |
| 2 | 使い方の誤り | なし |
| 3 | トレースの書き込みの失敗(開けない、途中で書けない、閉じるときの失敗) | なし |
| 4 | トレースを有効にしたのに `OMP_NUM_THREADS` が未設定、または引数のスレッド数と食い違う。引数を読んだ直後、`readParameters`・`params.txt` の書き出し(`src/offline_main.cpp` 29 行)・`FileOutput`(47 行)より前に検査する | なし(`trace.bin` も出力のファイルも作らない) |
| 5 | 範囲外の経路での停止(BL-017 の経路、識別子が `NONE` に達した) | 理由 1 または 2 |

- `run_trace.sh` は、終了コード 3 のときだけ同じ条件で1回やり直し、やり直したことと理由を `meta.txt` に書く。やり直しても 3 なら、B の実行なので停止して報告する(仕様 §7)。終了コード 4 は手順の誤りなので、やり直さずに止まる。

### 3.5 段階のくくり出しと再実行の道具

- くくり出しは手順1で、記録より先に入れる(挙動を変えない改造なので、完了条件1のビット一致だけで確かめられる)。対象は、`process_measures` に直接書かれた S1b の最初のフレームの処理、S2b、S3b・S3c、S0、組の中の予測の前後の時刻の計算、S7 の後の点の変換。S9 は `publish_odometry`(274 行)がすでに関数なので、くくり出さない(道具の側で `MappingOutput` を用意する)。手順2〜6の記録は、くくり出した関数の中か、呼び出しの前後に置く。
- 道具は本体と同じ YAML を読み、`readParameters` と `mapping_init` を呼ぶ。先頭の YAML の SHA256 を照合してから再実行する。`Q_output`・`P_init_output` はくくり出しで足す関数から取る。
- 段階の与え方は仕様 §5.3 のとおり。S7・S8 の地図は仕様 §5.1 のとおり B の iVox に作る。

### 3.6 照合器

- 形式の検証器(`trace_format.py`): 先頭、各段階のペイロード(条件つきの項目を含む、仕様 §4.3)、終わりのレコードを読み、不正なファイルを落とす。段階の読み手は、その段階の記録を足す手順で足す。間引きの規則の検査(記録の中の `s7`・フレーム・分岐・点ごとの項目から仕様 §6 の規則を計算し直し、S7 の入口の「共分散を記録するか」と一致すること)もここに置く。
- `compare_trace.py`:
  - J2: 1つの記録の中の入口と出口を、仕様 §3.2 の対応で比べる(3.1 の必須の再計算を含む)
  - J1: 2つの記録の J1 の項目を `call` の順に比べる
  - J3・J4 の差の有無: 同じ段階について、記録の出口と、再実行の道具の出口の J3・J4 の項目が一致するかだけを見る。与え方は仕様 §5.4 のとおり、改変前の B の記録の入口を与えて段階を再実行する(完了条件3では、注入した写しからビルドした道具で再実行する)。自走の記録どうしでは比べない(前の段階の差が後の段階に伝わり、注入した段階が最初の不一致にならないため)。閾値と許容誤差は使わない(人の判断。本番の閾値での照合は、範囲ごとのプランで作る)。J3 の「例外」の項目(仕様 §4.3 の S7 の点ごとの表)は比べない
  - J5: 記録の NaN/Inf の有無の集計と、終わりのレコードの有無と理由(仕様 §1、§7)。完全と発散の検査のどちらの記録でも数える
  - 最初の不一致の `call` と段階を出す(仕様 §5.4)
- 浮動小数点の値はビット列で比べる(仕様 §5.4)。

### 3.7 合成の入力

- 小さな PLIN: 開発用の入力ファイルの先頭を、レコードの区切りで切り出す(PLIN はレコードの列なので、区切りで切っても正しいファイルになる。[harness-input-format.md](../../docs/harness-input-format.md))。IMU の初期化、初期地図、組のループ、S8 まで通る長さにする(長さは手順7で決める)。仕様 §6 により、合成入力では間引かない(書き手に「間引かない」の引数を足す)。
- BL-017 の経路: 上の PLIN の、初期地図の後の LiDAR レコード1件の点をすべて `blind` の内側に動かし、前処理の結果を0点にする。前処理の結果が空の点群は受信で捨てられる(仕様 §1)ので、捨てられずに S2b の出力が0点になる入力を作れるかは手順8で確かめる(要確認5)。

## 4. テスト影響範囲

- 維持する挙動: トレースを無効にした `pointlio_offline` の出力(`traj.tum`、`odom.bin`、`cloud.bin`、`cloud_frames.txt`、`params.txt`)が、改造の直前の B と両 bag でビット一致すること(完了条件1)。B の本体を変えた手順の終わりに、そのたびに確かめ、手順17で判定に使う B のコミットでもう一度確かめる。
- ROS の経路(`pointlio_mapping`)も同じソースを使う。手順0で取る改造の直前の B の ROS の実行を基準に、手順17で T8 を走らせる。
- 数学の L1(`math_tests`)とゴールデン出力の照合(`run_math_golden.sh check`)は、改造が `include/IKFoM/` と `src/Estimator.cpp` に入るので、手順ごとに走らせる。ゴールデン出力は変えない。

- T7・T9〜T12・T14 の基準は A のもので、このプランでは走らせない(報告に残す)。

1. 照合器と検証器を Python にするか。完全な記録は 10 GB を超えうるので、純粋な Python では J2 の必須の再計算に長くかかる見込み(推測、未計測)。手順2で読みと xxHash64 の速さを測る。遅すぎれば、照合器の一部を C++ にする案を報告し、人が決める。
