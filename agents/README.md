# 開発ルールと手順

作業内容に合うルールを読み、変更ごとの設計と検証条件は plans/ へ記録する。

## 作業前に読むルール

複数の領域を変更する場合は、該当するルールをすべて読む。

| 作業 | ルール |
| --- | --- |
| テスト・ゴールデン出力・許容誤差を扱う | [testing.md](rules/testing.md) |
| C++ を Rust へ移植する、unsafe を書く | [rust-port.md](rules/rust-port.md) |

## ルールを足す・変える

ルールは作業のたびに読まれるので、密度を保つ。

- 新しいルールは、次の3つをすべて満たすものだけ足す
  1. 自明でない: 慣れた人でも、書かれていなければ間違える
  2. 繰り返す: 同じ間違いが2回以上起きた
  3. 具体的: 守り方が1つに決まる指示である
- 構造の説明(ディレクトリの中身、データの流れ)は書かない。書くのは避けるべき罠である
- エージェントは通常の作業中にルールを書き換えない。追加案は報告に書き、足すかは人が決める。足すときは、理由を添えて専用のコミットにする
- 既存ルールの言い換えや明確化はいつでも歓迎する

## 移植を進める

1. [プランのひな形](plans/template.md)をコピーし、モジュール名がわかる名前で plans/ に保存する(例: `plans/ivox.md`)
2. プランを、実装とは別のセッションでレビューする
3. 「新規テストケース」を先にテストへ落とし、Red(失敗)を確認してから実装する
4. 実装後、別セッションで差分をレビューする。渡すのは差分と、判定の基準(プラン・ルール)だけで、実装の経緯は渡さない
5. 完了時にプランの状態・検証結果・未検証の範囲を更新する

Claude Code がプランとレビューを、Codex が実装を担当するときの手順は [codex-handoff.md](codex-handoff.md)(B のバグ修正にも使う)。

## バグ台帳

疑いは「仮説 → 再現済み → 分類済み」で管理する。分類は (a) メモリ/UB系、(b) アルゴリズム/仕様系、(c) 未確認。テスト化してよいのは再現済みのものだけ。置き場所は [docs/bug-ledger.md](../docs/bug-ledger.md)。
