# Point-LIO Rust再実装 検証計画

作成日: 2026-10-21

## 目的と方針

Point-LIO(本リポジトリ: grid-map付きfork)をRustで再実装したとき、精度・性能・安全性がどれだけ変わるかを測る。そのために、再実装の前にC++側のバグを調査し、証拠のあるものだけをテスト化してRust実装の基準とする。

**核となる設計: 3系統比較**

- A: 現状のC++(as-is)
- B: C++でバグ修正したもの
- C: Rust実装

A→Bの差がバグ修正の効果、B→Cの差が言語・実装の効果。A→Cの直接比較はしない(要因が混ざるため)。

**前提(リポジトリ確認済み)**

- ROS1ベース。コアは約6千行(laserMapping, Estimator, IMU_Processing, preprocess, li_initialization)
- 地図はikd-treeではなくiVox(`include/ivox/`)
- 状態推定はIKFoM(`esekfom.hpp` + MTK。Eigenのテンプレート重め)
- センサ設定は avia / horizon / ouster64 / velodyne16
- テストは未整備(`Log/` にデバッグ出力があるのみ)

**原則**

- 「バグを出し切る」ことは目標にしない。再現できた疑いだけをテストにする
- 最新知見やLLMレビューは仮説の生成源であり、正しさの根拠ではない
- 指標と許容誤差は結果を見る前に決める

## フェーズ0: 土台づくり(約1週間)

1. **評価データの固定**: 公開bagを2〜3本選ぶ(Avia系1本、Ouster/Velodyne系1本、動的環境1本)。SHA256とバージョンを記録
2. **ROS非依存の実行ハーネス**: bagから点群とIMUを時刻順にファイルへ落とし、C++/Rust双方に同じ入力を渡す。laserMapping.cppからROS依存を薄く剥がす。改造前後で出力が一致することを確認
3. **指標と許容誤差の事前登録**
   - 精度: ATE/RPE(evo等)、地図点群のChamfer距離
   - 性能: フレームあたり処理時間(p50/p95/p99)、ピークメモリ、CPU使用率
   - 安定性: 発散回数、同一入力での実行間ばらつき
4. **Aのベースライン確立**: as-isのC++を10回実行し、非決定性(スレッド、浮動小数点)のばらつきを測る。Rustの許容誤差はこのばらつきを基準にする

## フェーズ1: バグ調査(2〜3週間、期限固定)

| 手段 | 狙い |
|---|---|
| ASan/UBSan/MSanビルド + フェーズ0データで実行 | メモリ・未初期化・未定義動作 |
| TSan | 前処理/メインループ間のデータ競合 |
| clang-tidy / cppcheck | 静的な疑い |
| 手動 + LLMレビュー | 仮説の生成(時刻同期、共分散、座標変換、境界条件、iVox探索) |
| 摂動テスト | IMU欠落、時刻逆転、点数ゼロ、外れ値 |

**台帳管理**: 疑いは「仮説 → 再現済み → 分類済み」の状態で管理する。

**分類**

- (a) メモリ/UB系: Rustで構造的に消える。「消えた数」として測定対象にする
- (b) アルゴリズム/仕様系: 直す / 仕様として固定 / 保留を人が決め、決定を記録
- (c) 未確認: テスト化しない

**終了条件**: 期限到達、または新規の再現済みバグが1週間出ないこと。

## フェーズ2: Bの作成とテスト固定(1〜2週間)

1. (b)のうち「直す」と決めたものだけをC++で修正してBとする。1件ごとにコミット
2. **ゴールデン出力の固定**
   - 単体: IKFoMの1ステップ(入力状態・観測 → 出力状態・共分散)、iVox近傍探索、IMU前処理、点群の歪み補正
   - 結合: データセットごとの軌跡と地図(許容誤差つき)
   - 性質ベース: 回転の直交性、共分散の対称性と半正定値性、時刻の単調性
3. 各バグに「Aでは失敗しBでは通る」回帰テストを1つ付ける

## フェーズ3: Rust実装(4〜8週間)

モジュール単位で移植し、各モジュールがフェーズ2の単体テストを通ってから次へ進む。

1. 順序: IMU前処理 → 点群前処理 → iVox → IKFoM相当(nalgebraで多様体を実装)→ 測定更新 → メインループ
2. 移植初期はスレッド構成もC++に合わせる。並列化などRustらしい最適化は等価性が取れた後に別コミットで行う
3. テストの誤りが疑われたら黙って直さず、台帳に起票してから判断する

## フェーズ4: 比較と報告(1〜2週間)

差分は A→B と B→C に分けて報告する。

- 精度差(許容誤差内か)
- 性能差(処理時間分布、メモリ)
- 安全性(サニタイザで出たエラー数、Rust側のunsafe行数)
- 実装コスト(LOC、工数、詰まった点: Eigen/MTK相当、ROS連携)

**条件統一**: 同一CPU、固定クロック、同一最適化レベル。`-O3 -march=native` の有無を明記する。

## リスク

- **IKFoM/MTKの移植が最大の山**。テンプレートで多様体を合成しているため、Rust側は手書きの状態型になる可能性が高く、工数を最も多く見込む
- 浮動小数点の演算順の違いで差が増幅し、軌跡が分岐する可能性がある。軌跡全体の一致ではなく、ステップ単位の差と統計指標で判定する
- ROS非依存化の改造がA自体の挙動を変えるリスク。改造前後の出力一致で確認する

## 最初の一歩

1. 評価bagの選定と取得
2. サニタイザ付きビルド(ASan + UBSan)の成立確認
3. 許容誤差を決めるためのAの10回実行
