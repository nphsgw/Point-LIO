# Point-LIO Rust再実装 検証計画

作成日: 2026-10-21。改訂: 2026-10-26(第2版)。

状態: **第2版。§1・§3・§6 の方針は承認済み(2026-10-26、人の判断。末尾の「決定事項」)**。合否の判定(§4)は、[事前登録](metrics-preregistration.md)の2回目の改訂として承認済み(2026-10-26)。

## 目的と方針

Point-LIO(本リポジトリ: grid-map付きfork)をRustで再実装したとき、精度・性能・安全性がどれだけ変わるかを測る。そのために、再実装の前にC++側のバグを調査し、証拠のあるものだけをテスト化してRust実装の基準とする。

**原則**

- 「バグを出し切る」ことは目標にしない。再現できた疑いだけをテストにする
- 最新知見やLLMレビューは仮説の生成源であり、正しさの根拠ではない
- 指標と許容誤差は結果を見る前に決める
- 判定の道具そのものも検証する。合否の判定は、意図的に入れた誤りで落ちることを確かめてから使う

**前提(リポジトリ確認済み)**

- ROS1ベース。主要モジュール(laserMapping, Estimator, IMU_Processing, preprocess, li_initialization, parameters の .cpp と .h)は上流 `4b86a46` で約3.6千行。IKFoM・iVox は別
- 地図はikd-treeではなくiVox(`include/ivox/`)
- 状態推定はIKFoM(`esekfom.hpp` + MTK。Eigenのテンプレート重め)。範囲内のモード(`use_imu_as_input: false`)では `kf_output` を使う。状態 `state_output` は pos, rot(SO3), offset_R_L_I(SO3), offset_T_L_I, vel, omg, acc, gravity, bg, ba の順で、誤差状態は30次元(`include/common_lib.h`)
- 出力の姿勢の共分散(`/aft_mapped_to_init`、`odom.bin`)は代入がなく常に0([台帳](bug-ledger.md) BL-004)。状態共分散を見るにはトレース(§5)が要る
- センサ設定は avia / horizon / ouster64 / velodyne16
- テストはハーネスの T1〜T14 のみ(フェーズ0)。部品単位のテストはない

## 1. 比較の定義(何を主張できるか)

| 比較 | 主張できること | 各系統に許す変更 |
| --- | --- | --- |
| A → B | 採用した修正の効果 | A: 上流 `4b86a46` と、挙動を変えないハーネス化だけ(タグ `A-v1` = `3dc49bc`)。B: 台帳で承認された修正だけ。メモリ/UB 系も含む。1件ごとにコミット |
| B → C | 移植の効果。言語・数値ライブラリ(Eigen→nalgebra など)・メモリ配置・探索順を含む。言語だけの効果とは主張しない | C: B のアルゴリズム・演算順・スレッド構成を保つ。避けられない違い(ライブラリの演算順など)は一覧にする |
| C → D | 設計変更・最適化の効果 | D: 並列化、データ構造の変更、演算順の変更。C の完成(§6)より後にだけ作る |

A→C は直接比べない(要因が混ざるため)。

- A のハーネス化が挙動を変えないことの根拠: 改造前の基準(`29f045e`。C++ のソースは `4b86a46` と同一)と、`3dc49bc` の ROS 経路の出力が、開発用の2本・正準設定の範囲でビット一致した(T8、[ros-free-harness.md](../agents/plans/ros-free-harness.md) §10)。ほかのデータ・設定では確かめていない。
- 「B は検証済み」と書くときは、検証した対象・条件・既知の制約(台帳で未修正のもの、未調査の範囲)を必ず添える。B は同等性の基準であって、正しさの証明ではない。
- 範囲: `use_imu_as_input: false`、`prop_at_freq_of_imu: true`、`check_satu: true`(両正準設定の値。`eval/config/canonical/`)。センサは Livox(CustomMsg)と Ouster(PointCloud2)。ほかのモードは範囲外として報告に書く。

## 2. 評価の3層

3層は独立した成果物にする。L2 が通っても L1・L3 が悪ければ「B と同じだけ悪い」と報告する。L2 の判定(事前登録の J1〜J4)が落ちたら、L1・L3 が保たれていても通過扱いにせず、停止して報告する。ライブラリの演算順などによる差は、J4 の (a, r) と J3 の例外の中に収まる範囲でだけ許し、原因を避けられない違いの一覧に載せる。

| 層 | 基準 | 分かること | 成果物 | 適用 |
| --- | --- | --- | --- | --- |
| L1 正しさ | 解析解、数値微分、真値の分かる合成運動 | C++ と Rust が同じ誤りを共有していないか | C++ から独立した数学・物理のテスト群 | A・B・C(・D) |
| L2 同等性 | B の部品・処理段階ごとの出力 | 移植で挙動が変わっていないか | 部品と段階のゴールデン出力、トレースの比較(§5) | B と C |
| L3 SLAM としての品質 | 地上真値、成功率(発散回数)、退化・飽和・長時間の試験 | 実際に使える推定器か | 品質評価の報告 | A・B・C(・D) |

3層とは別に、次の3つを報告の柱として持つ。

- **性能**: フレームあたり処理時間(p50/p95/p99)、ピークメモリ、CPU 使用率。同一CPU、固定クロック、同一最適化レベルで測り、`-O3 -march=native` の有無を明記する。合否にしない
- **安全性**: 同じ摂動・ファズの入力(§3)で、異常終了・NaN/Inf・サニタイザの検出の件数を系統ごとに数える。Rust 側は `unsafe` の箇所数と行数
- **再現性**: 入力・ソース・依存・設定を、タグ、イメージのダイジェスト、SHA256、作業ツリーの差分、判定の道具の版で辿れること

## 3. 故障の条件から入力を設計する

検証したい条件ごとに、合成入力・部品試験・実データのどれで確かめるかを割り当てる。

| 条件 | 合成 | 部品 | 実データ |
| --- | --- | --- | --- |
| 初期化、静止、既知の並進・回転 | ○(真値) | ○(IMU 前処理、初期化) | — |
| IMU 飽和と、その直前・直後 | ○(閾値の境界) | ○(飽和判定。`Estimator.cpp` の `0.99 * satu_gyro` など) | 激しい運動の bag(要選定) |
| センサ時刻のずれ、同一時刻、時刻の逆行 | ○(摂動) | ○(受信処理) | 既存 bag に摂動を加える |
| 観測の不足、平面・廊下などの退化 | ○ | ○(LiDAR 更新) | 退化を含む bag(要選定) |
| 点の欠損・重複、入力の終端 | ○(摂動) | ○(前処理) | 既存 bag に摂動を加える |
| 長時間の動作、地図の容量到達 | ○(iVox の LRU 退避) | ○(iVox) | 長いシーケンス(要選定) |
| 通常の運動 | — | — | 既存の2本(回帰試験) |

- 摂動と合成入力は [PLIN 形式](harness-input-format.md)で作る。A・B・C(・D)が同じものを読める。
- **ファズ**は、PLIN のレコード(種別、時刻、ペイロードの長さと中身)を変異させた入力とする。生成器と変異の種類は、フェーズ0の項目6で決める。
- データを2組に分ける。
  - **開発用**: 既存の2本([evaluation-data.md](evaluation-data.md))と合成データ。何度使ってもよい。
  - **最終評価用**: 未使用の正解つきシーケンス(激しい運動・飽和、退化、長時間)。候補を選び、SHA256 を記録したうえで、C が完成するまで実行しない。特定の bag への合わせ込みを防ぐため。D は封印を解いた後に作るので、D の報告ではこのデータへの合わせ込みを防げていないと明記する。D にも封印した組が要るなら、選定のときに別の組を取り分ける。

## 4. 合否の判定

B→C の合否は、[事前登録](metrics-preregistration.md)の J1〜J6 で決める(2026-10-26 承認。理由と、改訂の時点で見ていた結果は[改訂案](metrics-preregistration-revision-proposal.md))。

| 名前 | 対象 | 判定 |
| --- | --- | --- |
| J1 自走の契約 | 入力だけで決まる量(フレームの区切り、使った IMU の列、捨てた件数、段階の呼び出しの列と時刻・dt、出力の時刻と件数) | C を自走させ、B と完全一致 |
| J2 配線 | 自走した C の段階の間の受け渡し | ビット一致 |
| J3 段階の離散的な契約 | 使った点、近傍点、更新の成否、`valid`、飽和の判定、iVox への挿入・退避 | 各段階に B の入力を与え、完全一致。例外は計算値の閾値の近くだけ(件数の上限つき) |
| J4 1ステップの数値 | 状態の更新・Jacobian・共分散 | 同じ与え方で、\|c − b\| ≤ a + r·\|b\|。(a, r) は範囲ごとに移植の前に登録 |
| J5 発散 | C の全実行 | 発散0回 |
| J6 正解に対する非劣化 | ouster-nc-quad-easy の各実行 | 正解に対する ATE ≤ Δ_gt + B の変種の幅 |

τ を合否の境界にしない理由: avia では演算順の変種だけで ATE が 0.10 m 動く([fp-order-sensitivity.md](fp-order-sensitivity.md))。これを境界にすると、それより小さい移植の誤りを通してしまう。τ・RPE・Chamfer は感度分析として報告する。

## 5. 内部トレースの要件

- **目的**: 「最初にどの処理段階で契約が破れたか」を特定すること。大量のログを取ることではない。
- **段階**: 受信・同期 → 前処理 → 初期化 → 予測 → IMU 更新 → LiDAR 更新(点ごと)→ 地図更新。これらの呼び出しをイベントループとして記録する。入力イベントの ID を起点に、各段階を ID で対応づける。段階の間の対応(どの入力がどの段階の出力から来るか)を表にする。段階は一列の鎖とは限らない。
- **記録点**: §4 の判定に要るものを、各段階の入口と出口で取る(入口は、J3・J4 で C の1段階に与える B の入力になる)。
  - J1: フレームの区切り(`lidar_beg_time`・`lidar_end_time`)、予測・IMU 更新に使った IMU のレコードの ID、捨てたレコード、段階の呼び出しの列と時刻・dt・フラグ、出力の時刻
  - J3: 使った点(点ごとの採否、`effct_feat_num`)、近傍点の ID(挿入の通し番号)、反復の `valid` と更新の成否、`satu_check`、iVox への挿入・退避
  - J4: 状態(全成分)、内部の共分散(30×30。範囲外のモードは 24×24)、残差 `z`、Jacobian `h_x`、予測の入力(`angvel_avr`・`acc_avr`)
  - 段階の入力を完全にするための隠れた状態: `imu_last`・`imu_next`、`time_predict_last_const`、`time_update_last`、`is_first_frame`、前処理の出力の点群と `time_seq`、初期化の出力
- **形式は C++ と Rust に共通の契約**: PLIN 形式と同じく仕様書にする。Rust を書く前に決める。J4 の間引きの規則と、LiDAR 更新段階に与える地図の作り方も、この仕様で決める。
- **完了条件**:
  1. トレースの有効・無効で出力がビット一致する
  2. B の各段階を、記録した入力だけで再実行し、出力が記録とビット一致する(トレースの完全性)
  3. 意図的に入れた誤りを、正しい段階で最初の不一致として特定できる
- 既存の出力(`odom.bin`、`cloud.bin`)を拡張するか別の経路にするかは、この要件で決める。この設計が要る証拠として、次を仕様書に引用する。
  - T7・T8 は、時刻と件数を合否に使っていなかった(2026-10-26 に修正。下の「既存の資産の分類」)
  - 出力の共分散は常に0で、状態共分散の NaN/Inf(事前登録の発散の定義 (b))を出力からは検出できない(BL-004)

## 6. 移植を始める条件(移す範囲ごと)

ある範囲を移植し始めるには、その範囲について次の5つが揃っていること。

1. モード、座標系、単位、状態・誤差状態の定義(並び、摂動の左右、クォータニオンの成分順)が文書になっている
2. その範囲に関わる B の修正と、未解決の事項が台帳で辿れる
3. その範囲の L1 のテストと、L2 の差分試験(ゴールデン出力、トレースの記録点)が実行できる
4. 入力・ソース・依存・設定が再現できる(タグ、イメージのダイジェスト、SHA256、作業ツリーの差分、判定の道具の版)
5. その範囲の合否の判定が、意図的に入れた誤りを検出できる(注入による確認)

B 全体の完成は移植の前提にしない。範囲ごとに上の5つを満たせば始めてよい。

**移す順番**: 数学と状態の表現(SO(3)、多様体の boxplus/boxminus、状態の型。S2 は範囲内の状態で使われないので除く)→ 前処理(点群の前処理と IMU 前処理)→ iVox → 推定器(予測・IMU 更新・LiDAR 更新)→ イベントループ。

**C の完成点**: すべての範囲が L2 を通り、L1 を満たし、開発用データで L3 の非劣化を確かめてあること。C 側の条件4(Rust のツールチェーンの版、`Cargo.lock`)が記録され、L3 の判定(Δ_gt)が注入で落ちることを確かめてあること。D はこの後に作る。

2. **ROS非依存の実行ハーネス**: bagから点群とIMUを時刻順にファイルへ落とし、C++/Rust双方に同じ入力を渡す。改造前後で出力が一致することを確認
3. **指標と許容誤差の事前登録**
4. **Aのベースライン確立**: ハーネス経由で A を実行し、演算順の変種の幅を測る(事前登録の規則3・4)
5. **再現性と判定の道具**
   - A のタグ。環境の固定(Dockerfile のベースイメージのダイジェスト、直接入れるパッケージの版、`livox_ros_driver` のコミット)と、全パッケージの照合。メタデータの拡張(CPU、コンパイラの版、作業ツリーの差分そのもの、スレッド数)。判定の道具(作業用 venv)の版の記録
   - 判定漏れの修正(T7・T8 の時刻と件数)と、注入による確認
   - バグ台帳([bug-ledger.md](bug-ledger.md))
6. **トレースの仕様と実装**(§5)、状態・誤差状態の定義の文書(§6 の条件1)、条件表(§3)に沿った合成・摂動・ファズの入力の生成器、性能の計測系、サニタイザでの実行

完了条件: §6 の条件4(A について)。条件1(状態の定義の文書)。§5 のトレースの完了条件3つ。ハーネスの判定(T1〜T14)についての条件5。

4. 各バグに「Aでは失敗しBでは通る」回帰テストを1つ付ける
5. B のタグと、そのときの環境の記録

### フェーズ4: 比較と報告

差分は A→B、B→C に分けて報告する。各比較で、3層(L1・L2・L3)と、性能・安全性・再現性を並べる。最終評価用のデータは、ここで初めて実行する。

- 実装コスト(LOC、工数、詰まった点: Eigen/MTK相当、ROS連携)も添える

完了条件: A・B・C のすべてについて、開発用と最終評価用のデータで3層と性能・安全性を測り、各実行の再現情報(タグ、イメージ、SHA256、`meta.txt`)が報告から辿れること。未検証の範囲を報告に書くこと。

### フェーズ5: D(C の完成後)

並列化、データ構造の変更、演算順の変更。C との差を、C→D として L1・L3 と性能で報告する。L2(B との同等性)は求めない。最終評価用のデータは封印を解いた後なので、その旨を報告に書く(§3)。

完了条件: D について、C と同じ L1・L3・性能・安全性の測定と再現情報が揃うこと。

## リスク

- **IKFoM/MTKの移植が最大の山**。テンプレートで多様体を合成しているため、Rust側は手書きの状態型になる。数学と状態の表現を最初に移すのはこのため
- 浮動小数点の演算順の違いで差が増幅し、軌跡が分岐する(avia では ATE 0.10 m)。累積の差は合否にせず、段階ごとの比較と品質の非劣化で見る
- ROS非依存化の改造がA自体の挙動を変えるリスク。T8 で改造前後のビット一致を確認済み(開発用の2本と正準設定の範囲)
- 事前登録の再改訂: 2026-10-26 の改訂は V0・V1 の結果を見た後だった。今回の案は C と V2〜V4 の結果を見る前に出すが、すでに見た結果を改訂案に明記し、別レビューを経る
- 最終評価用のデータを開発中に使うと、合わせ込みを防げなくなる。C の完成まで実行しない
- 固定した apt の版が配布元から消えると、イメージを作り直せなくなる(黙って別の版にはならず、ビルドが失敗する)。既存のイメージは `point-lio-noetic:2026-10-21` として残す

## 決定事項(2026-10-31、人の判断)

1. 数学と状態の表現の範囲の (a, r) を承認し、付録に登録する(`efc461e`)
