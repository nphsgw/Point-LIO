## 実行条件(比較する実行すべてで固定して記録する)

- 同一マシン、同一 Docker イメージ(イメージ ID を記録)
- `OMP_NUM_THREADS` を記録する(設定しない場合は未設定と記録する)。`MP_PROC_NUM` はコードで使われておらず(`src/`・`include/` に参照がない)、`OMP_NUM_THREADS=1` でも出力は既定とビット一致した
- 最適化フラグ(`-O3`、`-march=native`、`-ffast-math` の有無)をビルドログで確認して記録する
- 入力は bag を最初から最後まで、同じ順序で与える。再生速度の影響を避けるため、実時間再生ではなく入力ファイル経由(フェーズ0の実行ハーネス)で比較する。ハーネスができるまで、性能の数値は登録対象にしない
- 各構成(A、B、C)につき10回実行する

## 精度の指標

ツールは `evo`(バージョンを記録)。

1. **ATE**: 並進 RMSE [m]。SE(3) アラインメント(スケールなし)。
2. **RPE**: 並進誤差 RMSE [m] と回転誤差 RMSE [deg]。区間は 1 s と 10 m の2通り。
3. **Chamfer 距離** [m]: 最終地図(各フレームのダウンサンプル済みワールド点を、初期地図構築後の全フレームについて累積した点群)をボクセル 0.1 m で間引いた点群同士の対称 Chamfer 距離(各点から最近傍までの距離の平均を、双方向で平均する)。

ouster-nc-quad-easy は正解に対する ATE/RPE を出す。avia-quick-shack は、正解がないため次の相対値だけを出す(報告だけ)。

- 構成 X の軌跡の、A の中央値実行(後述)に対する ATE/RPE

## 安定性の指標

- **発散**: 次のいずれかを満たす実行を1回と数える。(a) 異常終了、(b) 状態や共分散に NaN/Inf、(c) 隣接フレーム間の並進が 10 m を超える。状態と共分散は内部トレースで見る(出力の姿勢の共分散は常に0、[台帳](bug-ledger.md) BL-004)。
- **実行間ばらつき**: 同一構成の10回実行の、上の各指標の最小・最大・標準偏差。

## 性能の指標

- フレームあたり処理時間(1フレームの前処理から状態更新まで)の p50 / p95 / p99。最初の10フレームは除く。
- ピークメモリ(最大常駐セット、RSS)。
- 平均 CPU 使用率。

性能は合否にしない。A→B と B→C の比と分布を報告するだけとする。

## 演算順の変種と感度分析

A と B の実行から、次の手順で機械的に求める。ここで求める τ・RPE・Chamfer は感度分析として報告し、合否には使わない。Δ_gt は判定 J6 に使う。

1. 精度の各指標について、A(既定のビルド)の10回の値の最小・最大を出す。
2. **中央値実行**: 10回のうち、他の9回との ATE の中央値が最小の1回。
3. **演算順の変種**: ソースを変えずに、IEEE の意味を保ったまま演算順・丸めだけが変わる次の5通りでビルドする(`-ffast-math` は使わない)。コンパイラはイメージの gcc 9.4 のみ。
   - V0: 既定(`-O3`。上の1・2の10回と同じビルド)
   - V1: `-march=native`(FMA と AVX)
   - V2: `-mfma`(FMA と AVX。gcc の `-mfma` は AVX を含む。AVX2 以降なし)
   - V3: `-mavx2 -ffp-contract=off`(ベクトル化のみ。FMA なし)
   - V4: `-march=native -ffp-contract=off`(AVX のみ。積和の結合なし)
   `-march=native` は実行機の CPU に依存する(現機は AMD Ryzen 7 7700X)。CPU を記録し、比べる実行はすべて同じ機械で行う。V1〜V4 は各2回実行し、同じ変種の2回が一致するかを記録する。一致しない変種は、全実行を次の組に含める。
4. **変種の幅 τ**(感度分析) = 変種どうしの全組(各変種の代表実行、V0 は中央値実行。5変種なら10組)の ATE の最大値。RPE と Chamfer も同様に、組ごとの値の最大値。同じ変種の中の揺れが変種どうしより大きい指標は、その最大値を使う。最大値を使うのは、10回では分布の裾が見えないため。
5. **正解に対する精度の上限**(ouster-nc-quad-easy のみ): Δ_gt = **B** の変種(3 と同じ5通り)の代表実行の、正解に対する ATE の最大値。あわせて、その最小値との差(幅)を求める。C を B と比べるため、A ではなく B から求める。
6. B についても 3・4 を行い、B の幅 τ_B を出す。τ_B が A の τ を超える指標があれば報告する(修正で演算順への感度が変わった)。判定は止めない。

## 判定

A→B は差を報告する。合否にしない。B→C の合否は、次の J1〜J6 のすべてで決める。

### 1. 処理段階と前提

- 内部トレース([計画書](rust-reimplementation-verification-plan.md) §5)は、次の段階の入口と出口を記録する: 受信・同期、前処理、初期化、予測、IMU 更新、LiDAR 更新(点ごと)、地図更新、イベントループ(段階の呼び出し)。段階の間の対応(どの入力がどの段階の出力から来るか)は、トレースの仕様で表にする。
- **トレースの完全性**(J3・J4 を使う前提): B の各段階を、B が記録した入力だけで再実行し、出力が B の記録とビット一致すること。
- **点の並びの仕様**: ダウンサンプルと時刻でのソートが作る点の時刻と並びは、B で仕様として定め(台帳 BL-007)、C はそれを再現する。

### 2. 判定の一覧

| 名前 | 比べ方 | 合格の条件 |
| --- | --- | --- |
| J1 自走の契約 | C を入力の最初から最後まで自走させ、B の自走と比べる | 入力だけで決まる量が完全一致: 受信・同期のフレームの区切り(`lidar_beg_time`・`lidar_end_time`)、フレームの処理中に予測・IMU 更新に使った IMU のレコードの列、捨てたレコード、段階の呼び出し列とその時刻・dt・フラグ(状態の値に依存するもの、例えば更新の成否は除く)、出力の時刻と件数 |
| J2 配線 | 自走した C の中で、各段階の入力と、その入力を出した段階の出力を比べる | ビット一致 |
| J3 段階の離散的な契約 | 各段階に B の入力(状態を含む)を与えて C の1段階を実行し、B の出力と比べる | 離散的な出力(使った点、近傍点、更新の成否、反復の `valid`、飽和の判定、iVox への挿入・退避)が完全一致。例外は 3 節だけ |
| J4 1ステップの数値 | J3 と同じ与え方 | 各成分で \|c − b\| ≤ a + r·\|b\|。回転は boxminus(接空間)で比べる。NaN/Inf は不通過 |
| J5 発散 | C の全実行(両 bag、10回ずつ) | 発散0回 |
| J6 正解に対する非劣化 | C の各実行(ouster-nc-quad-easy、10回それぞれ) | 正解に対する ATE ≤ Δ_gt + (B の変種の代表実行の、正解に対する ATE の最大 − 最小) |

- **適用する範囲**: J1〜J4 は、開発用の2本の全フレーム・全段階と、計画書 §3 の条件表の合成入力に適用する。J1〜J3 は間引かない。間引きは J4 にだけ許し、その規則はトレースの仕様で、C の結果を見る前に登録する。
- 範囲内の設定(`publish_odometry_without_downsample: false`)では、`publish_odometry` の呼ばれ方は入力だけで決まる。設定を広げるときは J1 の項目を見直す。

### 3. 閾値の例外(J3)

- 対象は、入力が演算順に依存して計算される量と閾値の比較だけ: 平面の判定(`esti_plane` の `plane_thr`)、`p_norm > match_s * pd2 * pd2`、iVox の格子座標の floor と地図への追加の判定、近傍点の選び方(距離が等しい点と、k 番目と k+1 番目の距離の差が幅 w の中にある点。`nth_element` による並びの違いを含む)、近傍の候補の距離の上限(`d < max_range²`)。
- 入力だけで決まる比較(飽和の判定、ダウンサンプルのボクセルの割り当て)は対象にしない。
- 幅 w は、比べる量に J4 の (a, r) を伝播させて機械的に決める。
- 例外の件数は、C の判定が B と異なり、かつ B の量が閾値から w の中にあったものとする。B の量が w の外にあって判定が異なれば、不通過。
- 例外に当たった段階の J4 は、B の判定を C に強制して行う。
- 例外の件数の上限を登録する。上限を超えたら不通過。

### 4. 基準の登録

- (a, r)、例外の幅の決め方、例外の件数の上限は、範囲ごとに、その範囲の C の最初のコミットより前のコミットで、下の付録に、導いた根拠を添えて登録する。登録には人の承認が要る。
- A と B の変種どうしの1ステップの差は、登録の後に測る。内部トレースを使う範囲(前処理から後)では、B の変種どうしで測る: B の V0 で記録した入口を、V1〜V4 のビルドの B に与えて段階を再実行し、V0 の記録の出口と各変種の再実行の出口を、変種どうしの全組(5変種なら10組。累積の τ と同じ組)で比べる。変種のビルドの再実行は、そのビルドの本体の経路と演算の結合まで同じとは限らない(V0 では完了条件2のビット一致が保証になるが、ほかの変種には保証がない)。測った差はこの限界つきで扱う。A にはトレースがないので、この範囲では A の変種の1ステップの差は測らない。登録の前に測った場合は、その結果を付録に開示する。差が登録した基準を超えた場合は、基準を広げて通さず、停止して報告する。
- J4 の固定の摂動(5 節)が、(a, r) の上限を兼ねる。この上限を超える基準が要る段階が出た場合は、停止して報告する。
- LiDAR 更新段階に与える地図は、B が記録した挿入の列から C の iVox を作って与える。点の ID は挿入の通し番号とする。

### 5. 注入による確認(各判定を使う前の前提条件)

各判定は、使う前に、意図的に入れた誤りで落ちることを確かめる。注入は比べられる側に入れる(C ができる前は、B を改変した版を C の代わりに使う)。落ちない判定は使わない。停止して報告し、判定か記録点を作り直してから、確認をやり直す。確認の前の判定の結果は、合否として扱わない。

- J4 は、次がすべて落ちることを条件にする。移植で起こりうる誤り(f32 での累積、boxplus の左右の取り違え、クォータニオンの成分順、Jacobian の1項の欠落、dt の1つずれ)。固定の摂動(各段階で、出力のうち |b| が最大の成分に、f64 なら相対 1e-9、f32 なら 4 ulp を加える)。
- 判定ごとの注入は、[改訂案](metrics-preregistration-revision-proposal.md) 第4節の表のとおり。

### 6. 停止

J1〜J6 のどれかが落ちた場合、基準を広げて通さず、停止して報告する。

## 改訂履歴

- 2026-10-26(1回目): 許容誤差の規則 3〜8 を改訂(人の承認による)。旧規則は「τ = A の10回どうしの最大値。τ が0に近くても下限なし」だった。A は同じビルドでは決定的で(ROS 経路で44回ビット一致)、旧規則の τ は ATE で 1e-16〜1e-15 m になる。一方、ビルドフラグだけを変えた A で ATE が 8 mm〜0.10 m 変わり([fp-order-sensitivity.md](fp-order-sensitivity.md))、旧規則では正しい移植でも B→C が不通過になる。旧規則の意図(同じ実装の自然な揺れの幅)に合わせ、演算順の変種の幅を τ とした。**この改訂は、V0・V1 の差の大きさ(上の文書)を見た後に行った。** V2〜V4 の結果と、C の結果は見ていない。
- 2026-10-26(2回目): B→C の合否を、τ による累積の判定から、J1〜J6 に組み替えた(人の承認による。別セッションのレビュー3回)。τ・RPE・Chamfer は感度分析に下げた。旧規則8は報告だけにした。スレッド数の記録を `MP_PROC_NUM` から `OMP_NUM_THREADS` に改め、「A は既定値と1スレッドの両方を測る」を削った。ステップ単位の許容誤差の登録の時点を、「フェーズ2の単体ゴールデン出力を作る時点」から「範囲ごとに、その範囲の C の最初のコミットより前」に改めた。理由と、改訂の時点ですでに見ていた結果は[改訂案](metrics-preregistration-revision-proposal.md)の第1節と第3節。**この改訂は、V0・V1 相当の差、ouster の正解に対する ATE の幅(約 0.0005 m)、別プロジェクトでの Point-LIO の結果を見た後に行った。** V2〜V4、B、C、最終評価用のデータの結果は見ていない。
- 2026-11-01(3回目): J3 の閾値の例外の対象に、近傍の候補の距離の上限(`include/ivox/ivox3d_node.hpp` 164 行の `d < max_range * max_range`)を加えた(人の承認による)。距離は状態から計算した世界座標の点で決まるので、丸めの違いで候補に入るかが変わり、近傍点が5点に満たないかの判定まで変わりうる。ほかの閾値と同じ扱いにした。トレースの仕様 v2 の別セッションのレビューで指摘された。**この改訂は、開発用の2本での B の出力(BL-007・BL-010 の修正の前後の ATE)を見た後に行った。** 前処理から後の範囲の C の結果はまだ無い(C は数学と状態の表現の範囲だけ)。
- 2026-11-01(4回目): 判定4節の「A と B の変種どうしの1ステップの差」を、内部トレースを使う範囲では B の変種どうしで測ることにした(人の承認による)。トレースは B の V0 だけで記録し(記録の処理を足すと、ほかのビルドでは演算の結合が変わりうるため)、A には記録の処理を入れない。範囲内の数値の段階で A と B は大きく違わない見込みで(推測)、A に記録の処理を入れると、BL-012 を直していない A 専用の近傍点の記録が要る。トレースの仕様 v3 の別セッションのレビューで指摘された。**この改訂の時点で見た結果は、3回目の改訂のときと同じ。** 変種どうしの1ステップの差は、まだ測っていない。
- 2026-11-01(5回目): 4回目の改訂で決めた B の変種どうしの1ステップの差を、V0 と各変種の組だけでなく、変種どうしの全組で測ることにした(人の承認による)。累積の τ(感度分析)と同じ組にそろえるため。どの変種の再実行も同じ入口から出るので、追加の記録は要らない。あわせて、変種のビルドの再実行が本体の経路と同じとは限らないという限界を明記した。トレースの仕様 v4 の別セッションのレビューで指摘された。**この改訂の時点で見た結果は、3回目の改訂のときと同じ。**

## 事前に決めていない点(承認時に確認)

- RPE の区間(1 s と 10 m)、Chamfer のボクセル(0.1 m)、発散判定の 10 m、除外する最初の10フレーム。いずれも私の仮定

## 付録: 範囲ごとの基準
