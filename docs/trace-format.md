## 1. 目的と範囲

- 目的: 「最初にどの処理段階で契約が破れたか」を特定する。J1〜J5 の判定に要るものだけを記録する。
- 範囲: [state-definition.md](state-definition.md) 第1節のモード。`kf_input` の経路と、範囲内で通らない分岐は記録しない。通らない分岐は次のとおり。
  - `time_seq.size() > 0` の偽の側(`src/laserMapping.cpp` 704 行から)。`time_compressing` は必ず1件以上を返す
  - `sync_packages` の `lose_lid` の側。受信で空の点群を捨てるので、`lidar_buffer` に空の点群は入らない
  - `flg_reset` の側
  - IMU の初期化と初期地図の作成が終わった後に `feats_down_size == 0` になる経路(台帳 BL-017)。範囲外の読み出しは組のループで起きる。S2b の出力が0点で、S3b でも S3c でも終わらない(`after_imu_init_` が真で、初期地図ができている)フレームでは、S0 を呼ぶ前に、記録を止めて異常終了する。S3b・S3c で終わるフレームは S2b の出力を使わないので、0点でも止めない
- 範囲外の経路での停止: 上の BL-017 の経路と、数え上げが `NONE` に達した場合は、トレースが有効な B は止まり、無効な B は進む。このため完了条件1の比較は成り立たない。B がこの経路に入ったら、例外として通さず、停止して報告する。C がこの経路で止まったら、J5 の発散の (a) 異常終了に数える(2026-11-01、人の判断)。どちらの書き手も、検出して止めるときは理由のコードつきの終わりのレコード(第7節)を書いてから異常終了する。検出せずに落ちた場合は終わりのレコードがなく、ファイルは不正になる。これも J5 の (a) に数える
- 記録する経路: `pointlio_offline` だけで記録する。ROS の経路は購読のスレッドとメインループが並んで動く(台帳 BL-002)ので、J1 の列が実行ごとに変わりうる。`pointlio_offline` は1つのスレッドで、入力を1件読むたびに `sync_packages` を回す(`src/offline_main.cpp` 50〜69 行)。C も同じ順で回す。
- 記録するビルド:
  - B は V0(正準のビルド。`-O3`、FMA なし、`-march=native` なし)だけで記録する。V1 などでは、記録のための処理を足したことでインライン展開が変わり、FMA への結合も変わりうる(推測)。
  - C は `rust/run.sh build --release --locked --offline` のビルドだけで記録する。`RUSTFLAGS` と `target-cpu` は指定しない(CLAUDE.md の「Rust ビルド・テスト」)。
  - B の変種どうしの1ステップの差は、V0 で記録した入口を V1〜V4 のビルドの B に与えて段階を再実行し、V0 の記録の出口と各変種の再実行の出口を、変種どうしの全組で比べて測る。変種のビルドの再実行は、そのビルドの本体の経路と演算の結合まで同じとは限らない(V0 には完了条件2の保証があるが、ほかの変種にはない)。A にはトレースがないので、A の変種の1ステップの差は測らない(事前登録 判定4節、2026-11-01 の4回目と5回目の改訂)。1ステップの差は、入口の全体を記録から与えられる呼び出しだけで測る: S4i・S4g のすべて、S5・S6 のすべて、共分散を記録した S7。共分散を記録していない S7 は第5.3節の連鎖でしか再実行できず、連鎖を変種のビルドで回すと共分散が前の段階の変種の結果を引き継いで、累積の差になるため。
- 記録は値を読むだけで、計算を変えない。確かめ方は完了条件1(第8節)。B に入れる改造は第4.5節。
- 有効と無効の切り替え: 1つのバイナリ(`pointlio_offline`)の実行時の引数で有効にし、種類(第1.2節)と出力先を指定する。コンパイル時の切り替えは使わない(有効と無効が別のバイナリになり、完了条件1が同じ機械語どうしの比較でなくなるため)。C も同じ。
- 段階の再実行の道具(第5.3節・第5.4節、上の変種の1ステップの差): B では、本体と同じソースファイルを同じフラグでビルドした別の実行ファイルにし、本体と同じ関数(`kf_output.predict`、`update_iterated_dyn_share_IMU`、`update_iterated_dyn_share_modified`、`h_model_output`、iVox の `AddPoints`・`GetClosestPoint` など)を呼ぶ。段階の計算を道具の中で書き直さない。同じ関数でも、呼び出し側が違うとインライン展開と結合が変わりうるので、V0 で本体と一致することを完了条件2で確かめる。
- スレッド数: CMake は OpenMP のフラグを付けてビルドする(`CMakeLists.txt` 39〜41 行)。トレースを有効にした実行では `OMP_NUM_THREADS` を必ず設定し、未設定なら書き手は開始時に止まる(testing.md の、スレッド数を固定して記録する規則)。記録と再実行は、B と C で同じ値で行い、その値を先頭に書く(第7節)。値は実行の手順で決める。完了条件1で比べる実行(トレースを無効にした実行と、改造の前の B の実行)も同じ値で回す。B→C で比べる実行の値の規則は、事前登録の実行条件(6回目の改訂)。`OMP_NUM_THREADS` が未設定で書き手が開始時に止まった実行は、入力を読む前の手順の誤りなので、J5 に数えずにやり直す。Eigen の行列積が OpenMP で並列になるか、なるときに和の順が経路で変わるかは確かめていない(第9節)。
- 前提: 台帳 BL-012(近傍点の順序)の B での修正(`86911cb`、済み)。トレースは、この修正の後の B に実装する(第5.2節)。

### 1.1 既存の出力との関係

トレースは別のファイル(`trace.bin`)に書く。既存の出力(`odom.bin`、`cloud.bin` など。形式は `src/offline_output.h`)は変えない。根拠は次の2つ(計画書 §5 の求めによる引用)。

- T7・T8 は、時刻と件数を合否に使っていなかった(計画書「既存の資産の分類」。2026-10-26 に修正)。出力の比較だけに頼ると、件数や時刻のような契約が判定から漏れる。契約は、段階ごとの明示的な記録で比べる。
- 出力の姿勢の共分散は常に0で(台帳 BL-004)、状態共分散の NaN/Inf(事前登録の発散の定義 (b))を出力からは検出できない。状態共分散は、出力ではなくトレースで見る。

既存の出力を拡張しないのは、T8 などの既存のビット一致の比較を壊さないためでもある。

| 種類 | 内容 | 使う場面 |
| --- | --- | --- |
| 完全 | 第4.3節のすべての項目(共分散の全体と S7 の `z`・`h_x` は第6節の規則で間引く) | J1〜J4、完了条件1〜3 |

## 2. 識別子

すべて u32。値がないことを表す番兵は `NONE = 0xFFFFFFFF`。数え上げが `NONE` に達したら、記録を止めて異常終了する。

| 識別子 | 定義 |
| --- | --- |
| `rec` | PLIN の入力レコードの通し番号(0 から)。C++ では、受信のコールバックに渡すメッセージの `header.seq` に `rec + 1` を入れて持ち回す(0 は「代入されていない」を表す。`imu_last`・`imu_next` の既定値の `seq` は 0)。記録には `seq − 1` を書き、`seq` が 0 なら `NONE` を書く。`rec` が `NONE` の `imu_last`・`imu_next` は既定の値(すべてのフィールドが0の `sensor_msgs::Imu`。時刻も 0)を表し、再実行ではその値を与える。LiDAR は前処理の後に点群として積まれ、`seq` が失われるので、`time_buffer` と並ぶ `rec` の deque で持ち回す |
| `frame` | `sync_packages` が真を返したフレームの通し番号(0 から) |
| `grp` | フレーム内の時刻の組の番号 k(`time_seq` の添字)。LiDAR 更新は組ごとに1回 |
| `call` | 記録の通し番号(全体で 0 から)。すべての段階(S1a・S2a・S8・S9 を含む)の記録に振る。記録の主キーで、ファイル内の順と同じ |
| `s7` | S7 の呼び出しだけの通し番号(0 から)。間引きに使う |
| `pid` | iVox に挿入した点の通し番号(0 から)。初期地図(S3c)の挿入から数える。BL-012 の修正で、B は `IVoxNode` に点の配列と並ぶ `pid` の配列を持つ |

`frame` を持たない記録(S1a・S2a)では `frame` に `NONE` を書く。`grp` を持たない記録(S1a・S1b・S2a・S2b・S3a〜S3c・S8・S9)では `grp` に `NONE` を書く。待ち行列が空のときの「先頭の `rec`」も `NONE`。

`imu_deque` の中身は、受理した IMU の列(S1a の記録の順)の中で連続している。このため、待ち行列はどこでも「先頭の `rec` と件数」で表す。

## 4. 記録する項目

### 4.1 正規の並び

値は B のメモリ表現(Eigen の列優先、構造体の詰め物、MTK の内部)によらず、次の並びで書く。すべてリトルエンディアン。ハッシュも、この並びのバイト列にかける。

### 4.2 地図の要約のハッシュ

iVox の地図の要約を、次のバイト列の xxHash64 とする。セルを LRU の順(最後に作ったか、点を足したセルが先頭)に並べ、各セルについて キー(3個の i32)、点の数(u32)、点の `pid` の列(u32)をつなぐ。セルの中の点の順は挿入の順。点の座標は `pid` から挿入の記録で引けるので含めない。

LRU の規則(`include/ivox/ivox3d.h` 274〜298 行): 点を足すとき、そのセルがなければ作って先頭に置き、点を足す。作った後にセルの数が容量以上なら、末尾のセルを退避する。退避したセルの記録は、退避した順に並べる。セルがあれば点を足し、そのセルを先頭に移す。近傍の探索は順を動かさない。

### 4.3 段階ごとの項目

記録は、段階の入口(IN)と出口(OUT)の対、または1回の記録(EV)。各表の項目を、上から順にペイロードに書く。「条件」が書かれた項目は、条件が真のときだけ書く。条件は、同じペイロードの前の項目か、識別子で決まるものだけにする。記録そのものを書かない場合(呼ばなかった S5・S6 の IN・OUT、呼ばなかった S8 の OUT)は、表の外に書く。完全な記録では、書かない記録には `call` を振らない。「判定」の列は、その項目を使う判定。J2 は、すべての入口の項目と、それを出した段階の出口の項目の一致で見る(第3.2節)。入口の項目は、段階の関数に渡す実引数(または段階の中で読むその変数)から、呼び出しの直前に読む。正しい値の入った別の変数から書かない(書くと、前の段階の出口ではない値を渡す配線の誤りを J2 が見逃す)。例外は S5 の `time_update_last` で、呼び出しの前に書き換わるので、書き換わる前の値(dt_cov の計算に使った値)を読む(第3.2節の下)。

状態と共分散の記録の原則: S4i・S4g・S5・S6・S7 の出口には、状態の全体と、状態・共分散のハッシュを書く。入口には、状態と共分散のハッシュだけを書く(全体は直前の出口と同じなので、J2 はハッシュで見る)。共分散の全体は、第6節の規則で書く。

## 5. 段階の再実行(完了条件2、J3、J4)

### 5.1 地図の与え方

- S7・S8 に与える地図は、S3c と、そのフレームの直前までの S8 の挿入の列を、同じ順に iVox の `AddPoints` に通して作る。退避は挿入の途中で起きるので、別に適用せず、起きた退避が記録と一致することを確かめる。C で比べるときは C の iVox に、B の再実行(完了条件2)では B の iVox に適用する。挿入する点の座標は、S3c の出力の点と、S7 の出力の世界座標の点から、記録した添字で引く。近傍の探索は LRU の順序を動かさない(`include/ivox/ivox3d.h` 117〜224 行)ので、挿入の列から地図を再現できる。

- iVox への挿入の契約(J3 の S3c・S8)が一致していることが前提になる。

### 5.2 近傍点の順序

近傍点の列は J3 で順序つきで比べる。`esti_plane` は先頭の5点で解くので、順序は J4 の数値にも効く。

BL-012 の修正の前の B(`2750529` まで)では、順序が libstdc++ の `std::nth_element`(introselect)の内部で決まっていた。これを台帳 BL-012 に起票し、B で直した(2026-11-01 の人の判断、修正は `86911cb`)。修正後の仕様: 距離が範囲内の候補から、(距離, `pid`) の辞書順で小さい K 点(K = 5)を選び、その順に並べる。C はこの仕様を再現し、gcc の `nth_element` は写さない。

修正の後も、距離の計算の丸めで (距離, `pid`) の順が入れ替わる点や、候補が距離の上限をまたぐ点は、事前登録 判定3節の閾値の例外として扱う。そのための距離を S7 の出力に記録する(第4.3節)。

### 5.3 トレースの完全性(完了条件2)

B の各段階を、B の記録だけで再実行し、出口が記録とビット一致することを確かめる。再実行の入口は、その段階の入口の記録と、第3.2節の出所の出口の記録(状態の全体など)と、第5.1節の地図。

- **B 側での段階の与え方**: 記録した状態は、既存の `kf_output.x_` の各成分に代入して与える(MTK の添字の配列 `vect_state`・`SO3_state` を保つため。新しく作った `state_output` をそのまま代入すると添字の配列が空になり、`predict` の共分散のループが回らない。`include/IKFoM/IKFoM_toolkit/mtk/build_manifold.hpp` 186〜221 行、`esekfom.hpp` 152〜180 行。`change_x` は `x_` を添字の配列ごと上書きし、空なら作り直すので(`esekfom.hpp` 284〜295 行)、`change_x` で与えてもよい)。共分散は `change_P` で与える。時刻と IMU の変数(`time_predict_last_const`、`time_update_last`、`time_current`、`imu_last`・`imu_next`、`angvel_avr`・`acc_avr`)、`idx`・`k`・`time_seq`、組の点(`feats_down_body` の該当の範囲)を記録から与え、`pbody_list`・`crossmat_list` は組の点から作り直す。S7 の地図は第5.1節で B の iVox(`pid` つき)に作る。`Nearest_Points` は与えない(第3.2節)。

共分散を記録しなかった S7(第6節)は、入口の共分散がないので単独では再実行できない。次の連鎖で確かめる。

1. 共分散を変える段階は S5・S6・S7 だけで、S4i・S4g(`predict_state` だけ。`include/IKFoM/IKFoM_toolkit/esekfom/esekfom.hpp` 137〜182 行)は共分散に触れない。

### 5.4 J3・J4 の与え方と比べ方

- J3 の S7: 観測モデル(`h_model_output` に当たる部分)だけを、記録した入口の状態と第5.1節の地図で実行し、点ごとの項目、`valid`、分岐、有効点の数を比べる。観測モデルは共分散を参照しない(引数の `cov_p`・`cov_R` はコメントアウトされた行でしか使われていない、`src/Estimator.cpp` 218〜280 行)。更新の成否と分岐も観測モデルの結果だけで決まる(`esekfom.hpp` 189〜213 行)。このため、共分散を記録しなかった S7 も、すべて J3 にかける。
- J4 の S7: 共分散を記録した呼び出しだけで行う(入口の共分散がないと出口を比べられない)。閾値の例外に当たった点は、B の判定を C に強制する(事前登録 判定3節)。
- J4 の与え方: J3・J4 では、C の1段階に B の記録の入口を与え、C の出口を B の記録と比べる。このため J4 にかける呼び出しは B の記録で決まる。C の自走のトレースで共分散を記録する呼び出し(第6節の規則を C が自分の分岐と通し番号で選ぶ)は、J2 のハッシュの照合と発散の検査にだけ使い、J4 の可否には効かない。
- J4 の状態の回転(`rot`、`offset_R_L_I`): 事前登録の J4 のとおり boxminus で比べる。向きは c ⊟ b = Log(R_bᵀ R_c)(右からの摂動、[state-definition.md](state-definition.md) 第7節)で、比べる道具の側の Log を使う。範囲ごとに付録で別の比べ方を登録した場合はそれに従う(数学と状態の表現の範囲は、行列の成分ごと。計画書の 2026-10-31 の決定4)。トレースは回転行列の9値を記録するので、どちらでも比べられる。
- J4 の S9(付録に登録するときの案): `pos` は成分ごと。クォータニオンは、c と b の内積が負なら c の符号を反転してから成分ごとに比べる。Shoemake の分岐の違いは、符号と丸めの違いにしかならないので、J3 には入れない。比べ方は事前登録 判定4節により、その範囲の付録に登録するときに人の承認を得て確定する。
- 浮動小数点の値の一致: J1・J2、J3 の完全一致の項目(curvature など。S7 の点ごとの項目のうち「例外」のものは比べない)、完了条件1・2の比較は、浮動小数点の値をビット列で比べる(−0 と +0 は異なる)。J1 の項目に NaN があれば、ビット列が同じでも不通過とする。

- 合成入力では間引かない。
- 注入による確認(事前登録 判定 5 節)は、間引いた後の記録で行う。

見積もり(推測、未計測): ouster-nc-quad-easy は 1985 フレームで、組の数をフレームあたり約 6,500 と仮定すると、S7 と S4g は約 1,290 万回ずつになる。状態の全体(336 B)を出口だけに書いても、この2つで約 8.7 GB になる。入口と出口の両方に書くと約 17 GB になるので、入口はハッシュにした(第4.3節)。ほかに、S7 の点ごとの項目と世界座標の点が1点あたり約 100 B 加わる。S5・S6 では、IMU 1件あたり共分散の全体を3回(S5 の入口と出口、S6 の出口。約 21.6 KB)書く。ouster-nc-quad-easy の IMU は 19,902 件(入力のレコード数。`dt_cov > 0` の件数は数えていない)なので、多くて約 430 MB。合わせて 10 GB を超える見込み。BL-007 は修正済み(`80d49a1`)なので、組の数と1フレームの点の数を数えて、この見積もりと間隔 64・最初の 100 件を確定する(未実施)。

iVox の退避は、容量(1,000,000 セル。`include/ivox/ivox3d.h` 58 行の既定値で、設定からは変えられない)に達したときだけ起きる。正準設定の格子の大きさ(`ivox_grid_resolution: 2.0` m)では、開発用のデータで起きない見込みで、退避の契約(J3)は合成入力でだけ検出力を持つ。合成入力で起こすには、100 万セルを埋める広い範囲の点が要るので、実際に作れるかを確かめる(未確認)。

## 7. ファイル形式

PLIN と同じ方針で、1本の順序つきバイナリにする。リトルエンディアン。値の並びは第4.1節、ペイロードは第4.3節。

- 先頭: マジック `PLTRACE\0`(8 バイト)、版(u32、この版は 6)、次の項目。文字列は長さ(u32)とバイト列。
  - 記録の種類(u8。0: 完全、1: 発散の検査)
  - 書き手(u8。0: B、1: C)
  - ソースのコミット(文字列。40 桁の小文字の16進)と、作業ツリーに差分があるか(`B`)
  - ビルドの種類(文字列。B は `V0`、C は `release`)
  - コンパイラの版(文字列。B は `g++ --version` の1行目、C は `rustc --version` の出力。イメージの ID と同じく、実行の手順が調べて引数で渡す)
  - Docker イメージの ID(文字列。`sha256:` と 64 桁の小文字の16進。コンテナの中からは分からないので、実行の手順が引数で渡す)
  - スレッド数(文字列。`OMP_NUM_THREADS` の値。未設定の実行は第1節のとおり始まらない)と、CPU のモデル名(文字列。`lscpu` の Model name)。実行の手順が引数で渡す
  - 正準設定の YAML の SHA256(32 バイト)。B と C が同じファイルを読むので、設定のダンプの書式に依存しない
  - 入力の PLIN ファイルの SHA256(32 バイト)
  - 間引きの規則(間隔 64、最初の件数 100。各 u32)
  - 壁時計の時刻は書かない
  - 文字列は UTF-8 で、末尾の改行を含めない
  - 先頭は B と C で値が異なる
- B と C の記録の比べ方: どのレコードにもバイト一致は求めない。判定ごとに、第4.3節の「判定」の列でその判定に当たる項目だけを比べる(J1 は B と C の自走の記録の J1 の項目、J2 は C の記録の中の入口と出口、J3・J4 は第5.4節)。状態に依存する値と条件つきの項目があるので、ペイロード長も B と C で違いうる。比較器は、条件つきの項目を含めて、ペイロードを第4.3節のとおりに解釈する
- レコード: 段階(u8)、記録の種別(u8。1: IN、2: OUT、3: EV)、`call`・`frame`・`grp`(各 u32)、ペイロード長(u32)、ペイロード。
- 段階の番号: S1a=1、S1b=2、S2a=3、S2b=4、S3a=5、S3b=6、S3c=7、S0=8、S4i=9、S5=10、S6=11、S4g=12、S7=13、S9=14、S8=15、終わり=255。
- 終わりのレコード: 段階 255、種別 EV、`frame`・`grp` は `NONE`。`call` は、完全な記録で次に振る番号(発散の検査の記録でも同じ値)。ペイロードは、理由(u8。0: 正常に終わった、1: BL-017 の経路、2: 数え上げが `NONE` に達した)と、それまでに書いたレコードの数(u32。終わりのレコード自身を含めない)。終わりのレコードがないファイルと、途中で切れたレコードを含むファイルは不正とする(PLIN と同じ扱い)。
- 書き込みの失敗: 書き手は、トレースの書き込みに失敗したら、終わりのレコードを書かずに専用の終了コードで終わる。実行の手順は、この終了コードの実行を無効とし、同じ条件で1回だけやり直す。やり直しても失敗したら、J5 の (a) に数える。無効にした実行の件数と理由は報告に書く。やり直した実行は、J5・J6 の10回のうちの1回として数え、無効にした実行は数えない。B の実行で、やり直しても書き込みに失敗したら、B は判定の基準になるので J5 には数えず、停止して報告する。この規則は C の結果を見る前に決めた(2026-11-01、人の判断)。それ以外で終わりのレコードがないファイルは、J5 の (a) に数える(第1節)。
- 発散の検査の記録: S3b・S4i・S5・S6・S4g・S7 の OUT だけを書き、ペイロードは状態と共分散の NaN/Inf の有無(`B`、`B`)の2バイトだけにする。`call` には、同じ実行で完全な記録を書いた場合と同じ値を書く(完全な記録で書かれ、この種類では書かない記録の分も数える)。

## 8. 完了条件(計画書 §5)

1. 記録が計算を変えないこと。両 bag で次を確かめる。
   - B: トレースを無効にした出力(`odom.bin`、`cloud.bin` など)が、記録のための改造(第4.5節)を入れる直前の B のコミットの出力とビット一致する。改造は常に入っているので、有効と無効の比較だけでは確かめられないため
   - B: トレースを有効にした出力(完全、発散の検査のそれぞれ)が、無効にした出力とビット一致する
   - C: トレースを有効にした出力(完全、発散の検査のそれぞれ)が、無効にした出力とビット一致する。J5 は発散の検査を有効にした C の実行で見て、J6 はその実行の出力で見る(出力は無効の実行とビット一致するので、同じ実行を使える)
   - 記録が実行ごとに同じこと: 同じ入力で B を2回実行し、完全と発散の検査のそれぞれで `trace.bin` が先頭を含めてバイト一致する。C も同じ。記録のための新しいコードが、詰め物などの未初期化のバイトを読まないことを確かめるため(台帳 BL-001・BL-025〜027 の前例)
   - `pid` の配列は BL-012 の修正の一部で、記録のための改造ではない。その効果は A→B の差として測る
   - 判定と報告に使う B: A→B の差、J6 の Δ_gt と B の変種の幅を求める実行、最終評価の B は、記録のための改造を入れた後の B のコミット(B のタグを打つコミット)を使う。トレースを記録する B と同じにするため。V0 は、改造の前の B と出力がビット一致することを上で確かめる。V1〜V4 は確かめないので、改造の前後で出力が変わりうる(2026-11-01、人の判断)
2. B の各段階を、記録だけで再実行し、出口が記録とビット一致する(第5.3節)
3. 意図的に入れた誤り(事前登録 判定 5 節)を、正しい段階で最初の不一致として特定できる(第5.4節)。事前登録の注入に加えて、配線の誤り(段階に、前の段階の出口ではない状態を渡す)を入れ、J2 が検出することを確かめる。
   この条件の確かめ方として、トレースの道具そのものが誤りを検出することも確かめる。どれも、壊した入力で落ちることを先に確かめて(Red)から使う。
   - 完了条件2の検出力: 隠れた状態を1つ与えない再実行(例: S3a の `N`・`b_first_frame_`、S0 の `time_update_last`)が不一致になる
   - 読み手: 終わりのレコードのないファイル、途中で切れたレコード、ペイロード長と中身の食い違いを不正として扱う
   - 正規の並び(行優先、SO3 の行優先)とハッシュ: 合成の小さな PLIN から B と C が書いたトレースを、形式の検証器と照合器に通す契約テスト。項目を1つずつ壊して落ちることを確かめる。xxHash64 は参照実装のテストベクトルで確かめる(第4.1節)
