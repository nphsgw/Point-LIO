# 事前登録の改訂案: 合否の判定の構成

状態: **承認済み(2026-10-26、人の判断)。事前登録の本文に反映した([metrics-preregistration.md](metrics-preregistration.md) の2回目の改訂)**。別レビューを3回実施し、2回目と3回目の「条件つきで承認してよい」の条件(計12点)を人が決めて反映した。以後の正本は事前登録の本文で、この文書は改訂の理由と、改訂の時点で見ていた結果の記録として残す。

## 1. 改訂の理由(守りたい性質から)

現行の規則6は、B→C の合否を「B の中央値実行に対する ATE/RPE/Chamfer が τ 以下」で決める。τ は演算順の変種どうしの幅である。この境界には次の2つの欠点がある。

- **検出力がデータに依存する**: avia では、演算順の変種の違いだけで ATE が 0.10 m 動く([fp-order-sensitivity.md](fp-order-sensitivity.md))。τ がこの大きさになると、それより小さい移植の誤りは通ってしまう。例えば、ハーネスの注入で IMU 時刻を1件 1 ms ずらしたときの ATE は 7.9e-6 m だった(どちらの bag での結果かは記録にない)。
- **感度の低いデータでは、妥当な実装差まで落としうる**: τ は変種5通りの最大値にすぎず、C が使うライブラリ(nalgebra・libm)の演算順の違いを覆う保証はない。

累積の指標(ATE・RPE・Chamfer)は、全実行を走らせた後の差を見る。演算順が違えば最初の姿勢から軌跡がずれる(fp-order-sensitivity.md)ので、累積の差から移植の誤りと演算順の差を分けられない。

移植で守りたいのは「軌跡が B の変種の幅に入ること」ではなく、次の3つである。

1. 同じ入力に対し、同じ離散的な判断(フレームの区切り、使った IMU と点、更新の成否、飽和の判定、捨てた件数、出力の時刻、iVox への挿入・退避)をし、処理段階を同じ順序でつなぐ
2. 1ステップの数値が、演算の特性で説明できる誤差の中で B と一致する
3. 推定器としての品質が B より悪くならない

そこで、判定をこの3つに対応させて分ける。1と2で移植の誤りを検出し、3で品質を確かめる。

## 2. 改訂後の判定(案)

### 2.1 処理段階と前提

- トレース([計画書](rust-reimplementation-verification-plan.md) §5)は、次の段階の入口と出口を記録する: 受信・同期、前処理、初期化、予測、IMU 更新、LiDAR 更新(点ごと)、地図更新、イベントループ(段階の呼び出し)。段階の間の対応(どの入力がどの段階の出力から来るか)は、トレースの仕様で表にする。段階は一列の鎖とは限らない(LiDAR 更新は、予測・前処理・前フレームの地図更新の出力を同時に入力に持つ)。
- **トレースの完全性**(J3・J4 を使う前提): B の各段階を、B が記録した入力だけで再実行し、出力が B の記録とビット一致すること。グローバル変数に残る隠れた状態(`imu_last`・`imu_next`、`time_predict_last_const`、`time_update_last`、`is_first_frame`、`angvel_avr`・`acc_avr`、`Nearest_Points`、`h_model_output` の `k`・`idx` など)が記録から漏れていないことを、これで確かめる。
- **点の並びの仕様**: ダウンサンプル(PCL `VoxelGrid` の float32 の平均と、非安定のソート)と時刻での非安定のソートは、点の時刻と並びを実装の詳細に依存させる。B でこれを仕様として定める(安定のソート。等しいときは元の添字の順。ボクセル内の平均を足す順も定める)。C はその仕様を再現する。[台帳](bug-ledger.md) BL-007。

### 2.2 判定

| 名前 | 比べ方 | 合格の条件 |
| --- | --- | --- |
| J1 自走の契約 | C を入力の最初から最後まで自走させ、B の自走と比べる | 入力だけで決まる量が完全一致: 受信・同期のフレームの区切り(`lidar_beg_time`・`lidar_end_time`)、フレームの処理中に予測・IMU 更新に使った IMU のレコードの列、捨てたレコード、段階の呼び出し列とその時刻・dt・フラグ(状態の値に依存するもの、例えば更新の成否は除く)、出力の時刻と件数。範囲内の設定(`publish_odometry_without_downsample: false`)では、`publish_odometry` の呼ばれ方は入力だけで決まる |
| J2 配線 | 自走した C の中で、各段階の入力と、その入力を出した段階の出力を比べる(2.1 の対応表に従う) | ビット一致 |
| J3 段階の離散的な契約 | 各段階に B の入力(状態を含む)を与えて C の1段階を実行し、B の出力と比べる | 離散的な出力(使った点、近傍点、更新の成否、反復の `valid`、飽和の判定、iVox への挿入・退避)が完全一致。例外は 2.3 だけ |
| J4 1ステップの数値 | J3 と同じ与え方 | 各成分で \|c − b\| ≤ a + r·\|b\|。回転は boxminus(接空間)で比べる。NaN/Inf は不通過 |
| J5 発散 | C の全実行(両 bag、10回ずつ) | 発散0回(事前登録の定義: 異常終了、状態や共分散の NaN/Inf、隣接フレーム間の並進 10 m 超)。状態と共分散はトレースで見る(出力の共分散は常に0、BL-004) |
| J6 正解に対する非劣化 | C の各実行(ouster-nc-quad-easy、10回それぞれ) | 正解に対する ATE ≤ Δ_gt + (B の変種の代表実行の、正解に対する ATE の最大 − 最小)。Δ_gt は現行の規則5。落ちたら、境界を広げずに停止して報告する(規則7) |

- **適用する範囲**: J1〜J4 は、開発用の2本の全フレーム・全段階と、条件表([計画書](rust-reimplementation-verification-plan.md) §3)の合成入力に適用する。離散的な項目(J1〜J3)は間引かない。間引きは J4 にだけ許し、その規則はトレースの仕様で、C の結果を見る前に登録する。
- avia-quick-shack の累積の判定は J5 だけになる(正解がないため)。
- **合否から外す指標**: RPE、Chamfer、B に対する ATE は、合否に使わず感度分析として報告する。理由は第1節の累積の差の性質である。地図の同等性は J3(iVox への挿入・退避)で判定する。
- 現行の規則1〜5(中央値実行、変種 V0〜V4、τ と Δ_gt の求め方)は、感度分析と J6 のために残す。
- 現行の規則7(τ を広げて通さない)は、J1〜J6 の基準に読み替えて残す。
- 現行の規則8(τ_B が τ を超えたら止める)は、報告だけにする。B の変種の実行は、J6 と (a, r) の裏取りのために残す。

### 2.3 閾値の例外(J3)

- 対象は、入力が演算順に依存して計算される量と閾値の比較だけ:
  - 平面の判定(`esti_plane` の `plane_thr`)
  - `p_norm > match_s * pd2 * pd2`(`src/Estimator.cpp`)
  - iVox の格子座標の floor と、地図への追加の判定
  - 近傍点の選び方: 距離が等しい点(タイ)と、k 番目と k+1 番目の距離の差が幅 w の中にある点(近いタイ)。`nth_element` による並びの違いを含む
- 入力だけで決まる比較は対象にしない(幅 0)。飽和の判定(入力は IMU の値そのもの)と、ダウンサンプルのボクセルの割り当て(入力は機体座標の点で、並びは 2.1 の仕様で決まる)がこれに当たる。
- 幅 w は、比べる量に J4 の (a, r) を伝播させて機械的に決める。
- **例外の件数**は、C の判定が B と異なり、かつ B の量が閾値から w の中にあったものとする。B の量が w の外にあって判定が異なれば、それだけで不通過。
- 例外に当たった段階の数値の比較(J4)は、B の判定を C に強制して行う。
- 例外の件数の上限を登録する。上限を超えたら不通過。

### 2.4 基準の登録

- (a, r)、例外の幅の決め方、例外の件数の上限は、範囲ごとに、その範囲の C の最初のコミットより前のコミットで、事前登録の付録(範囲ごとの表)に、導いた根拠を添えて登録する。登録には人の承認が要る。
- A と B の変種(V0〜V4)どうしの1ステップの差は、登録の後に測る。登録の前に測った場合は、その結果を付録に開示する。差が登録した基準を超えた場合は、基準を広げて通さず、停止して報告する。
- J4 の固定の摂動(第4節)が、(a, r) の上限を兼ねる。この上限を超える基準が要る段階が出た場合は、停止して報告する。
- LiDAR 更新段階に与える地図は、B が記録した挿入の列から C の iVox を作って与える。点の ID は挿入の通し番号とする。詳細はトレースの仕様で決める。

### 未確定の点(後で決めてよいもの)

- 部品ごとの (a, r)、例外の幅、件数の上限の値。期限は 2.4 のとおり。
- 最終評価用のデータの L3 の基準。期限は、データを封印した後で、開発用のデータで C の L3 の結果を見るより前。
- J4 の間引きの規則と、地図の与え方の詳細。期限は、トレースの仕様を決めるとき(Rust を書く前)。

## 4. 注入による確認(各判定を使う前の前提条件)

各判定は、使う前に、意図的に入れた誤りで落ちることを確かめる(計画書 §6 の条件5)。注入は比べられる側に入れる。C ができる前は、B を改変した版を C の代わりに使う。入力ファイルに入れた誤りは B と C の両方が同じように読むので、どの判定でも落ちない。

**基準の大きさに依存しない注入**(J4 は、これらがすべて落ちることを条件にする):

- 移植で起こりうる誤り: f32 での累積、boxplus の左右の取り違え、クォータニオンの成分順、Jacobian の1項の欠落、dt の1つずれ
- 固定の摂動: 各段階で、出力のうち |b| が最大の成分に、f64 なら相対 1e-9、f32 なら 4 ulp を加える。これが (a, r) の上限を兼ねる(2.4)

**判定ごとの注入**:

| 注入(比べられる側) | 落ちるべき判定 |
| --- | --- |
| IMU のヘッダ時刻の読み取りを +1 ms | J1(予測の dt・時刻) |
| LiDAR のヘッダ時刻の読み取りを +1 ms | J1(フレームの区切り、出力の時刻) |
| レコードを1件読み飛ばす | J1(件数) |
| 予測と更新の呼び出し順を入れ替える | J1(呼び出し列) |
| ある段階に、出力元の段階の1つ前の出力を渡す | J2 |
| 飽和の閾値の向きを逆にする(`>=` を `<`) | J3(飽和の判定) |
| 反復の `valid` を反転する | J3(更新の成否) |
| iVox の容量を1つずらす | J3(退避)。開発用のデータでは退避が起きない見込みなので、合成入力で確かめる |
| 格子座標の floor を trunc にする | J3(挿入) |
| 状態または共分散に NaN を1つ | J4、J5 |
| 姿勢列に、時刻に比例して増える並進のずれを加える(SE(3) の整列で消えない。大きさは J6 の境界を確実に超えるように決める) | J6 |

落ちない判定があった場合は、その判定を使わない。停止して報告し、判定か記録点を作り直してから、同じ確認をやり直す。

現状: ハーネスの判定(T1〜T14)では、T2・T5・T6・T7・T10・T12・T14 で一部の注入を確認済み。T7・T8 は時刻と件数を合否に使うよう直し、時刻 +1 ms と1件欠落の注入で落ちることを確かめた(2026-10-26)。J1〜J6 についての確認は、トレースができてから行う。

## 5. 承認の手順

1. 別セッションでのレビュー(実施済み、3回)。渡した資料はこの文書、現行の事前登録、計画書、[testing.md](../agents/rules/testing.md) と、第3節の表の出典
2. 人が承認する
3. 承認したら、すぐに次を、理由と第3節の内容を添えて1つの専用のコミットで改める
   - 事前登録: 本文の許容誤差の規則と改訂履歴。冒頭の「いずれのバイナリの実行結果も見る前に書く」と「A の10回実行のばらつきから機械的に導く規則だけを決める」。ステップ単位の許容誤差の登録の時点(「フェーズ2の単体ゴールデン出力を作る時点」を 2.4 に合わせる)。「事前に決めていない点」の τ の最大値の項(感度分析での位置づけ)。avia-quick-shack の精度の扱い(累積の判定は J5 だけで、ほかは報告)。スレッド数(「`MP_PROC_NUM` を固定して記録する」と「A は既定値と1スレッドの両方を測る」を、「`OMP_NUM_THREADS` を記録する」に置き換える。`MP_PROC_NUM` はコードで使われず、`OMP_NUM_THREADS=1` でも出力が既定とビット一致したため)
   - [testing.md](../agents/rules/testing.md): 「許容誤差」の節(基準を変種の幅とする記述、判定を ATE/RPE/Chamfer で行う記述)と、「時刻と非決定性」の節の `MP_PROC_NUM` の記述
   - 計画書: §2(L2 を外れた差の扱いを、J3・J4 の不通過を停止とする扱いに合わせる)、§4(J1〜J6 の表)、§5(段階に受信・同期とイベントループを加え、記録点に J1〜J4 の項目を加える)
4. 第4節の確認と、2.1 のトレースの完全性は、各判定を使う前の前提条件とする。確認の前の判定の結果は、合否として扱わない
