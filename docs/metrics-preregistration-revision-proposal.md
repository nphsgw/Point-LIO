# 事前登録の改訂案: 合否の判定の構成

状態: **草案(2026-10-26)。別レビュー1回目の指摘を反映済み。2回目のレビューと人の承認が未実施**。この文書は[事前登録](metrics-preregistration.md)を変えない。承認されるまで、現行の規則(τ による B→C の判定)が有効である。改訂案を別レビューに出すことは人が決めた(2026-10-26、[計画書](rust-reimplementation-verification-plan.md)の「決定事項」3)。

## 1. 改訂の理由(守りたい性質から)

現行の規則6は、B→C の合否を「B の中央値実行に対する ATE/RPE/Chamfer が τ 以下」で決める。τ は演算順の変種どうしの幅である。この境界には次の2つの欠点がある。

- **検出力がデータに依存する**: avia では、演算順の変種の違いだけで ATE が 0.10 m 動く([fp-order-sensitivity.md](fp-order-sensitivity.md))。τ がこの大きさになると、それより小さい移植の誤りは通ってしまう。例えば、ハーネスの注入で IMU 時刻を1件 1 ms ずらしたときの ATE は 7.9e-6 m だった(どちらの bag での結果かは記録にない)。
- **感度の低いデータでは、妥当な実装差まで落としうる**: τ は変種5通りの最大値にすぎず、C が使うライブラリ(nalgebra・libm)の演算順の違いを覆う保証はない。

累積の指標(ATE・RPE・Chamfer)は、全実行を走らせた後の差を見る。演算順が違えば最初の姿勢から軌跡がずれる(fp-order-sensitivity.md)ので、累積の差から移植の誤りと演算順の差を分けられない。

移植で守りたいのは「軌跡が B の変種の幅に入ること」ではなく、次の3つである。

1. 同じ入力に対し、同じ離散的な判断(使った点、更新の成否、飽和の判定、捨てた件数、出力の時刻、iVox への挿入・退避)をする
2. 1ステップの数値が、演算の特性で説明できる誤差の中で B と一致する
3. 推定器としての品質が B より悪くならない

そこで、判定をこの3つに対応させて分ける。1と2で移植の誤りを検出し、3で品質を確かめる。

## 2. 改訂後の判定(案)

1と2は、全実行を走らせた出力どうしではなく、**段階ごとの比較**で判定する。トレース(計画書 §5)に記録した B の各段階の入力(状態を含む)を C の同じ段階に与え、その段階の出力を B の出力と比べる。こうすると、前の段階までの演算順の差が持ち込まれない。

| 対象 | 判定 | 基準の決め方 |
| --- | --- | --- |
| イベントの対応・順序・分岐 | 段階ごとの比較で完全一致 | 例外は、閾値で決まる判定(飽和の `0.99 * satu_gyro`、近傍の距離の閾値など)のうち、入力が閾値から登録した幅の中にあるものだけ。幅は閾値ごとに、C の結果を見る前に登録する。例外に当たった件数を報告する。それ以外の不一致は、件数によらず不通過とする |
| 状態の更新・Jacobian・共分散(1ステップ) | 段階ごとの比較で、各成分の誤差 \|c − b\| ≤ a + r·\|b\| | a(絶対)と r(相対)は、演算の特性(条件数、倍精度の ulp の倍数)から部品ごとに導き、部品のゴールデン出力を作る時点で、C の結果を見る前に登録する。0 に近い成分(バイアス、共分散の非対角成分)は a で扱う |
| 軌跡・地図(累積) | 正解に対する ATE が Δ_gt(現行の規則5)以下(ouster-nc-quad-easy) | 品質の非劣化の確認であり、移植の誤りの検出は上の2つが担う |

- **基準の裏取り**: B の変種(V0〜V4)どうしの1ステップの差も測る。導いた基準 (a, r) を変種どうしの差が超えた場合は、基準を広げて通さず、停止して報告する(現行の規則7と同じ扱い)。
- **合否から外す指標**: RPE と Chamfer、B に対する ATE は、合否に使わず感度分析として報告する。理由は第1節の累積の差の性質である。地図の同等性は、iVox への挿入・退避を離散的な契約に含めることで判定する。
- 現行の規則1〜5(中央値実行、変種 V0〜V4、τ と Δ_gt の求め方)は、感度分析と Δ_gt のために残す。
- 現行の規則7(τ を広げて通さない)は、上の各基準に読み替えて残す。
- 現行の規則8(τ_B が τ を超えたら止める)は、B の修正が演算順への感度を変えたことの報告として残す。B→C の判定を止める条件にするかは要確認。

### 未確定の点(要確認)

- avia-quick-shack には正解がない。累積の判定は ouster-nc-quad-easy だけになり、avia は段階ごとの比較と、感度分析の報告だけになる。これでよいか。
- Δ_gt を非劣化の境界にそのまま使うか、余裕を設けるか。余裕を設けるなら、C の結果を見る前に数値を決める。Δ_gt は上限だけを見るので、品質が Δ_gt に収まる範囲の誤りは累積の判定では検出しない(上の2つで検出する前提)。
- 1ステップの (a, r) の具体的な値と、閾値の例外の幅。部品ごとに決める。
- 最終評価用のデータの L3 の基準。正解つきなら Δ_gt と同じ求め方にするか。
- スレッド数の扱い。事前登録は「`MP_PROC_NUM` を固定して記録する」とするが、`MP_PROC_NUM` はコードで使われていない([ros-free-harness.md](../agents/plans/ros-free-harness.md) §9)。`OMP_NUM_THREADS=1` でも出力は既定とビット一致した。

## 4. 注入による確認(採用の条件)

改訂後の各判定は、使う前に、意図的に入れた誤りで落ちることを確かめる。段階を指定した摂動の大きさは、その部品の1ステップの基準 (a + r·|b|) の10倍とする。

| 注入 | 落ちるべき判定 |
| --- | --- |
| 状態または共分散に NaN を1つ | 1ステップ。累積(発散) |
| IMU のヘッダ時刻 +1 ms | 1ステップ(予測・IMU 更新の入力が変わる) |
| LiDAR のヘッダ時刻 +1 ms | 離散(出力の時刻) |
| 入力レコードの1件欠落 | 離散(件数) |
| レコード種別の入れ替え | 離散(順序) |
| 1フレームの点の一部欠落 | 離散(使った点) |
| 段階を指定した摂動(予測・IMU 更新・LiDAR 更新・地図更新のいずれか) | 1ステップ。トレースで、指定した段階が最初の不一致になる |

落ちない判定があった場合は採用しない。停止して報告し、判定か記録点を作り直してから、同じ確認をやり直す。

現状: ハーネスの判定(T1〜T14)では、T2・T5・T6・T7・T10・T12・T14 で一部の注入を確認済み。T7・T8 は時刻と件数を合否に使うよう直し、時刻 +1 ms と1件欠落の注入で落ちることを確かめた(2026-10-26)。改訂後の判定(段階ごとの比較)についての確認は、トレースができてから行う。出力の共分散は常に0なので、共分散の NaN の注入はトレースで行う。
