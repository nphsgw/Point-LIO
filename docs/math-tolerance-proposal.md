# 数学と状態の表現の基準(登録案)

状態: **承認済み(2026-10-30、人の判断)**。[事前登録](metrics-preregistration.md)の付録に登録した。この文書は導いた根拠の詳細。範囲は[計画書](rust-reimplementation-verification-plan.md) §6 の「数学と状態の表現」。この範囲の L2 は、ゴールデン出力(`golden/math`、13部品)との照合とする(2026-10-30 の決定)。

## 1. 前提

- C は f64 で計算し、積和の結合(`mul_add`、`target-cpu` の指定)を使わない。B の既定のビルド(V0、`-O3`、`-march` なし)も x86-64 の基本命令だけで、FMA を使わない。
- C は B と同じイメージを土台に動かす(2026-10-30 の決定)。`sin`・`cos`・`acos`・`atan2`・`sqrt` は同じ glibc の libm を呼ぶので、同じ引数には同じ結果を返す。
- C は B と同じ式・同じ分岐・同じ閾値を使う(計画書のフェーズ3)。
- 記号: u = 2⁻⁵³ ≈ 1.11e-16(丸めの単位)。|b| は B の値、‖b‖ は1つの記録の出力のうち、同じ区画の成分の絶対値の最大。

## 2. 上限

事前登録の判定 5 節の固定の摂動は、記録ごとに出力の最大成分へ相対 1e-9 を加える。この摂動を落とすには、その成分で a + r·|b| < 1e-9·|b| が必要になる。下の案は a = r·‖b‖ の形なので、r < 5e-10 が上限になる。

a を定数にしないのは、出力の小さい記録(回転角 1e-9 の Log の出力は 1e-9 程度)で、定数の a が固定の摂動を隠すため。

## 3. 案

| 部品 | a | r | 根拠 |
| --- | --- | --- | --- |
| `so3_log`、`so3_boxminus`、`state_boxminus`、`a_matrix` | 0 | 0(ビット一致) | 条件が悪く、導いた (a, r) が上限を超える(4節)。前提(同じ式・同じ順・同じ libm)のもとでは、ビット一致が成り立つはずの部品 |

| `quat_from_matrix` | r·‖b‖ | 64u | 同上。q と −q は同じ回転なので、⟨q_c, q_b⟩ < 0 なら q_c の符号を反転してから比べる |

## 4. ビット一致を求める理由

C がこれらの部品で B と和の順を変えると、次の条件の悪さによって差が拡大する。導いた r は、2節の上限 5e-10 を超える。

- `SO3::log`(A と同じ式の側、θ ≥ 1e-3): `acos` の条件数は 1/sin θ。そのうえ θ/sin θ で割る。トレースの丸め u から、出力の相対誤差は π の近くで ε/d²(d = π − θ)、0 の近くで u/θ² になる。ゴールデン出力の入力の範囲では、d ≥ 3.16e-4 で約 2e-9、θ ≥ 1e-3 で約 1e-10 になる。前者は上限を超える。BL-008 のテストで、A の式の誤差が ε/d² で増えることを確かめた(`So3Log.AccurateAroundNearPiBranch`)。
- `so3_boxminus`、`state_boxminus` の回転の区画: 内部で `SO3::log` を呼ぶ。
- `a_matrix`: (1 − cos θ)/θ² と (1 − sin θ/θ)/θ² は、小さい θ で桁が落ちる。`cos` の引数が 1 ulp 違うと、結果が大きく変わりうる。
- π ちょうどの入力では、Log の向き(±π·a)を K の符号で決める。K は丸めの雑音の大きさなので、計算の順が違えば向きが反転しうる。

C がこれらの部品でビット一致しなかった場合は、事前登録の判定 4 節のとおり、基準を広げずに停止して報告する。そのときの選択肢を、事前に挙げておく。

- B の式を条件のよいものに替える。例えば Log を全域で atan2 と対称な部分から求める。B が変わり、ゴールデン出力の作り直しと承認が要る。
- C で B の和の順を再現する。
